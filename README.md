# 挪车接客(parking)

一款微信小游戏方向的单机休闲解谜游戏,**双层复合玩法**:

- **下半屏**:挪车谜题(类 Parking Jam)。停满带箭头的车,点一下车就沿箭头直线开出;被挡住就开不出去,只会抖一下。开出的车停进上方的车位。
- **上半屏**:传送带式接客。彩色乘客站在一条循环轨道上绕圈走,走到轨道底部的**上车口**时,如果某个车位上停着**同色且未满**的车,这一组乘客就上车。车坐满自动开走,腾出车位。

**过关**:乘客池空 + 轨道上没人 + 车位全空 + 网格无车。
**死局**:车位全满、没有一辆车还能坐满、网格里也没有一辆车能开出去 —— 此时判负。

引擎 Cocos Creator **3.8.7**。当前有 10 个离线生成的关卡,每关 36 辆车。

---

## 目录结构

```
game/                 Cocos Creator 工程(用 Creator 打开这个目录)
  assets/main.scene   唯一场景
  assets/scripts/
    core/             纯逻辑层:不 import 'cc',可脱离引擎单测
    view/             表现层:import 'cc',负责建模、动画、HUD、相机
  assets/resources/levels/level-N.json   离线生成的关卡数据
logic/                核心层的测试与构建入口(jest + tsc 配置)
tools/                离线脚本:关卡生成、音效生成、模型减面、车辆模型体检
editor/               本地关卡编辑器(esbuild + 一个 node 静态服务)
docs/superpowers/     设计文档(specs/)与实施计划(plans/)
```

### 最重要的一条约定:core 不认识 Cocos

`core/` 里的任何文件都**不能** `import ... from 'cc'`。这是整个测试体系的地基 —— 一旦引入,jest 就再也加载不了这个文件,那条逻辑从此只能靠肉眼在编辑器里看。

因此分工是:

- **core 管拓扑**:谁挡住谁、哪一组乘客下一拍到上车口、这一关是否可解。
- **view 管几何**:世界坐标、缩放、缓动、材质。

但**几何约束本身住在 core**。例如轨道的形状、周长、每格弧长、一组乘客的排布(`track-shapes.ts` / `track-path.ts`)都在 core 里,因为 `validateTrack` 必须在关卡数据落盘之前就能判断"这个环长这个形状画不画得下"。view 从 core 读这些常量,不自己另存一份。

## 跑起来

### 玩

用 Cocos Creator 3.8.7 打开 `game/` 目录,打开 `assets/main.scene`,点预览。

### 两道闸门

改完代码必须都过:

```bash
cd logic
npm install              # 首次
npm test                 # core 的单元测试(jest)
npm run typecheck:view   # 表现层的类型检查(tsc,不跑测试)
```

`view/` 没有测试环境 —— 它 import 'cc',jest 加载不了。所以它的闸门只有类型检查,逻辑正确性靠把可测的部分推回 core。

### 看 core 到底怎么想的(调试叠加层)

预览里按 **D** 键,给每辆车画出 core 真正在推理的那个矩形:**绿色 = core 认为能开出去,粉色 = core 认为被挡**。

车没有端正地待在自己的框里,就说明它被画到了 core 没在看的地方 —— 那是表现层的 bug,core 的判定看起来会跟着一起错。同档位的车框永远一模一样;要是框对齐了而车身不一样大,那是车身错了,不是 `CAP_BOX` 错了。框画在车的**上方**(z = 1.2),正交相机下这不产生任何横向位移 —— 所以**框要是从车上滑开了,本身就证明投影不是正交的**。

### 真机预览:一条命令

```bash
cd logic
npm run preview            # 关项目 → 构建 → 出二维码
npm run preview:nobuild    # 跳过构建(已经在 Creator 界面里点过构建了)
```

**不用清缓存。** 那一步治不了任何东西 —— 详见下面「开了 MD5 缓存之后…」那条:预览报 `ENOENT` 是**这一次构建**制造出来的幽灵队列,不是上一次留下的脏数据。

真正起作用的只有**顺序**:开了 MD5 缓存的 Cocos 是先写原名、再改名成带哈希的,而开发者工具的文件监听(`wxfilewatcher.exe`)在项目打开期间会把**两个名字都**排进编译队列 —— 改名前那个在打包时早就不存在了。所以脚本做的就是 `close` → 构建 → `preview`,让 Cocos 写文件的时候没人在盯着那个目录。

**别用退出码判断构建成不成功。** Creator 的 CLI 是个 Electron 应用,正常退出也会给非零码 —— 实测 **exit 36**,而它自己的日志写着 `build Task (wechatgame) Finished in (12 s)`、`game.js`/`game.json` 也刚刚重写过。脚本因此**看产物**:目录是否自洽、文件是不是刚写的。

`npm run preview` 会自己起一个 Creator 实例来构建,所以它要求 **Creator 界面在这个项目上是关着的**。想留着界面改场景,就在界面里点构建、然后跑 `npm run preview:nobuild` —— 开发者工具那一侧照样由脚本处理。

两个工具的路径自动探测,探不到用环境变量顶:`WX_DEVTOOLS_CLI`(cli.bat)、`COCOS_CREATOR`(CocosCreator.exe)。`--dry-run` 只打印要执行的命令,`--image` 把二维码写成 PNG 而不是画在终端里。

### 重新生成关卡

关卡不是手写的,是离线算出来的:

```bash
cd logic
npm run gen
```

它把 `tools/gen-levels.ts` 和 core 一起编译到 `.tmp/gen`,用普通 node 跑一遍,写出 `game/assets/resources/levels/level-N.json`,并打印一张表(每关的车数、颜色数、初始被挡车数、难度分、乘客总数)。

> ⚠️ **现在十个 `level-*.json` 都是手改过的**(裸地 0 实验,见下文),`npm run gen` 会把它们覆盖回出厂档位。跑之前先决定实验是留还是退。

**改了 core 里任何影响关卡数据的东西(环长、容量、难度曲线),都要重跑一次 `npm run gen` 并把 JSON 一起提交**,否则运行时的关卡和代码里的规则会对不上。

```bash
cd editor
npm install

```

## 生成关卡的思路

关卡是**构造出来就一定可解**的,不是随机撒完再验证:

1. **pack**:先只摆形状,不定方向,把车填进网格。
2. **peel**:反复挑一辆"存在一个合法方向、且那个方向上有一条通路能开出去"的车,拿掉它。**剥离的顺序本身就是一份通关解法**。

早先的版本是随机撒 + 拒绝采样,密度到 75% 就再也撒不出可解局面了;换成 pack-then-peel 之后,36 辆车、超过 80% 的网格占用率都稳定可解。

难度曲线在 `level-gen.ts` 的 `TRACK_CURVE` 里,现在只剩两个旋钮:**每条候补通道显示几批乘客**,以及**有两条通道还是一条**。环长不再是旋钮 —— 由形状的周长唯一决定(见下)。

## 几个容易踩的不变量

这些都在代码注释里写着原因,这里只列出来提醒:

- **环长由形状决定**。每种轨道形状的合法环长由 `capacityOptions()` 算出,依据是"组与组之间的裸地(seam)"要落在 `SEAM_MIN..SEAM_MAX` 之间 —— 太小看不出行,太大看着空。目前四种四边形是 28 格,圆形 24 格。
- **环长必须是 4 的倍数**,因为两条通道的入口在 `boardIndex ± capacity/4`,除不尽就会落到拐角上,而入口的法线必须接近水平。
- **`GROUP_SIZE` 必须能整除所有车容量(16 / 24 / 32)**。现在是 4(一横排 4 个人)。取 12 就不行 —— 会把一种颜色的乘客切成"若干满组 + 一个残组",轨道上出现半空的格子。
- **能把环压多紧,是拐角说了算**(上车口曾经是,现在不是了)。格子一短,拐角内侧的一排就会贴上前一排 —— `minRowGap` 量的就是这个,下限 `BLOCK.clearance` 等于人宽:不同组的人可以挨上,不能重叠。32 格时有三种形状过不了,所以 `CAPACITY_OPTIONS` 停在 28。
- **`minRowGap` 只比较相邻两格之间的距离**。它曾经把"同格内"的对也算进去 —— 而一排是刚体,同格内的距离恒等于 `acrossStep`,永远是最小值,于是拐角的测量被一个常量遮住了,`capacityOptions` 检查的是同义反复。改这个函数时别把同格的对加回去。
- **椭圆是最紧的那条曲线**。其他形状的拐角由 `RECT_R`/`HEX_R`/`TRAP_R` 决定,椭圆没有圆角参数,最紧曲率就是 `halfH²/halfW` —— 所以缩窄 `halfW` 时 `halfH` 不能跟着一起缩,否则椭圆先崩。
- **一排乘客本身比人略窄**(`acrossStep` 0.20 < 人宽 0.22,头部重叠约一成)。这不是失手 —— 决定"看不看得出行"的是**跨组最近距离与组内最近距离的比值**,所以把一排收窄能换来更小的组间缝。想改宽回去,缝就得同步放大。
- **`minRowGap` 量的是脚下那个点,画出来的是一个 0.22×0.55 的人 —— 差额靠深度补,不是靠间距**(`PAX_DEPTH`)。人是**躺在板面里**的(见 `trackReach`:头比脚高 0.55,却不朝相机凸出),而 `capacityOptions` 把它当成脚下一个直径 0.22 的点来校验。排距只有 0.33~0.38,所以一个人的身子要伸进**一排半以外**。实测五种形状在各自的出厂环长下,**不同格**的人有 **96~134 对**在屏幕上重叠,最狠的压掉一个人 **40%~53%** 的面积,而这些情况 `minRowGap` 全部合格(0.226~0.272 ≥ 0.22)。**校验没算错,它算的是错的立体。**
  间距解决不了:要给 0.55 高的身子让路,排距就得 0.55,环长从 24~28 掉到 ~16。深度可以,而且**免费** —— 相机是正交的、`BOARD_TILT` 是 0,z 在屏幕上什么都不改变,只决定谁在前面。`PAX_DEPTH` 现在是 **2.1**,来历见下一条(第一版取 1.6,在一帧静止画面上够,转起来不够)。整个环因此有 6.5 单位深,相机在 15 外。
  **同一条斜率也用在一排之内**:轨道走横向时,一排四个人是**竖着叠**的(间距 0.20,每人高 0.55),同组内的重叠和跨组一样多。所以 `layoutRow` 给每个人按**自己的 y** 算 z,行节点按**行的 y** 算 z,两者相加 —— 能相加是因为**行永远不旋转**。
- **深度斜率要按「转起来」的最坏情况标定,不能只看一帧静止画面**。`PAX_DEPTH` 第一版取 1.6 —— 在**某一个相位**上,五种形状每一对跨格重叠都被分开了一个人厚。但环是转的:把相位扫过一整格,最近的那一对在 y 上从 0.14 收到 **0.106**,于是 98690 对重叠里有 **714 对**在转动的某个瞬间厚度不足 0.22。**这是一个只有动起来才看得见的缺陷**,而它正是这样被报上来的。2.1 之后归零。凡是"位置随时间变"的几何量,标定就得沿时间扫,不能取一帧。
- **「把人立起来变成小球」试过,被否决了 —— 别再提议一次**。做法是给 `fit` 节点绕 X 转 90°,让人自己的轴指向相机;头是全身最宽的部件(0.22,身体 0.19,手臂垂下 0.10),于是整个人被自己的头挡住,屏幕上就是一颗球,和参考图一致。**几何上它赢得很干脆**:跨格重叠从 98690 对降到 5836 对,最坏重叠从压掉 60% 的身体降到 5%,而且 core 的 `minRowGap` 从此是**对的** —— 它一直把乘客当成脚下一个 0.22 的点在校验,球正好就是那个点。
  **否决的理由是玩法读不出来:一排四个人变成四颗挨着的球,人看不出"这一组有四个"。** 那个数字是玩家要判断的东西(一组能不能坐满某辆车),不是装饰。所以模型退回有胳膊的那一版。
  连带退回的还有三笔性能改动 —— 它们全都是"立起来"才买得到的:转整行代替逐个摆人(躺着转会把人转倒)、不建身体和手臂(躺着看得见)、每排一个深度值(躺着时同排四个人在顶部/底部是竖着叠的,需要各自的深度)。**唯一留下的是 `recolorPaxFigure` 的材质缓存**,它和模型无关。
- **现在两半赛道都是「裸地 0」,这是一次进行中的实验,不是出厂状态**。环上一排挨着一排,通道里也一排挨着一排。改了三处:`LANE.step` 0.34 → 0.22(通道,0.22 就是 `blockLength`,所以裸地正好是 0),十个关卡的 `capacity`/`boardIndex` 改成各自形状下裸地最接近 0 的那一档,以及构建标记 `0831-7`。
  **每个形状的那一档不一样,因为周长不一样** —— 按 `perimeter / blockLength` 向下取到 4 的倍数:`rect`/`hex`/`oval` **44**、`trap` **40**、`circle` **32**。`boardIndex` 必须恰好是 `capacity` 的一半。上一轮我用的 48 其实是**过头了**:`rect` 10.512 / 48 = 0.219,比一排的进深 0.22 还小,也就是排与排已经开始互相挤,44 才是真正的「刚好贴上」。
  **代价是量过的,而且是几何上的,不是审美上的**:不同组之间的最近距离(`minRowGap`,含拐角)全部低于 `clearance` 0.22 —— `circle` 差 0.034、`rect` 0.047、`trap` 0.049、`hex` 0.059、`oval` **0.077**(约三分之一个人)。`clearance` 存在的理由正是**两组重叠会把一组的颜色抹进另一组**,而颜色是玩家唯一要从环上读的信息。另外上车口的白带缺口(`GAP_ARC` 0.26)现在横跨 **1.06~1.18 格**,这一条只是外观,core 只看 `boardIndex`。
  **`SEAM_MIN`/`SEAM_MAX` 这两条边界没有动**,所以 `capacityOptions` 仍然只认到 28 —— 运行时的 `validateTrack` 只是 `console.warn`(见 `GameController`),不拦。这也意味着**`npm run gen` 会把这十个 JSON 全部覆盖回合法档位**。要退回:`LANE.step` 回 0.34,`capacity` 回 28(`circle` 24)、`boardIndex` 回一半。
  参考负载:环上 112 → **176 人**(`circle` 96 → 128),`LANE.step` 降到 0.22 还让通道能塞进更多批次(`rect` 5 → 7、`circle` 7 → 10),但这一轮**没有重新生成关卡**,所以 `lookahead` 仍是 5,通道只是变密变短,没有变长。
- **真机 8fps / 模拟器 49fps —— 差距在「全屏 pass」和「渲染器个数」上,不在逻辑量上**。两个抽到的大头:
  - **post-process 是一个全屏 pass**。`setupAntiAliasing` 把 `PostProcess` 挂到相机上做 FXAA —— 手机 1170×2532 就是 **296 万像素每帧重读重写一遇**,叠在场景之上。当初为了答「边缘发毛刺」加的,当时就标注了「需要真机验证」而那个验证一直没做。已去掉那一行调用(引擎模块还编译着,想恢复只需加回一行)。
  - **一个乘客曾是 4 个 `MeshRenderer`**(头/身/两臂各一个节点)。环上 112 人 + 两条通道 80 人 = **768 个渲染器**;引擎每帧要把它们全走一遍(变换、剪裁、填 instance buffer),而那一遍是 JS。现在整个人烧成**一个 mesh**(`figureMesh`),**768 → 192**。
  **为什么合得起来:四个部位本来就共用一个颜色、也就共用一个材质** —— 分立的渲染器从来没表达过任何东西。代价是**手臂被烤死**(一根要动的肢体就得有自己的节点、也就得有自己的渲染器),所以摆手一并删了,改成 `ARM_POSE_DEG` 一个固定的一前一后姿态。
  顺带的:环上每帧节点写入从 **364 降到 140**。
- **别把锯齿状的相位喂给正弦 —— 那不是摆动,是频闪**(`SWING_RATE`)。`phaseHolder.p` 每一拍都被**绝对重置**到 `-1/capacity` 再补间到 0(重置必须是绝对的,原因见那里的注释),所以它是一条**锯齿**。手臂摆动原本直接吃这个相位:每一拍正弦参数扫过 1.4286 弧度,然后在拍边界**原地跳回去**。实测 **112 条手臂在每个拍边界平均瞬跳 18°、最大 29°,每秒 5.9 次**。那不是一群人在走路,那是整片人一起抽。
  玩家的原话是真机上转起来"**有种眩晕感**",而**模拟器看着还行 —— 帧多,扫过的那一段看得见,跳的那一下只占你看到的一小部分**。改成用 `travel`(拍数 + 当前拍的进度,只增不减)驱动,跨拍连续。
  **通则:任何跨拍复用的动画量,先问它在拍边界连不连续。** 位置量已经踩过一次(那次是补间没交付完的差额逐拍累积,把整个环往后拖),这次是相位跳回。
- **一个「完整、新鲜、看起来没问题」的构建,可以是坏的 —— 白屏 + `Error 3817` 就是它**。构建在序列化场景时要去 **编辑器已编译的 chunk** 里查组件的类;项目冷启动时那些 chunk 还在写,日志里紧挨着的一行是 `... is not in module cache!`。**Cocos 不会因此让构建失败** —— 它往场景里写 `_components: [null]`,把其余任务全部跑完,产出一个文件齐全、时间新鲜、`game.js`/`game.json` 都在的目录。游戏于是启动即白屏,而唯一的线索是 `Error 3817 ... Arguments: GameController, 0`,引擎的意思是「index 0 那个组件是坏的,我把它删了」。
  **判断依据只能是构建日志**(`game/temp/builder/log/wechatgame*.log`),找 `is missing or invalid` / `Missing class:`;目录本身查不出来。实测 2026-08-31 当天 **9 次构建里坏了 1 次**,源码一个字没动 —— 是竞态,所以它多数时候会过,而且会在你什么都没改的时候失败。`tools/preview.mjs` 现在读日志把关,并且**只重试一次**(第一次构建已经把编辑器的类缓存烘热,第二次大概率就对了);两次都丢类就不是竞态,去 Creator 里找编译不过的脚本。
  排错时的三个坐标:场景源文件里组件是 `{"__id__": N}`、`main.scene` 里那个节点的 `__type__` 是压缩 uuid(前 5 位与 `.meta` 的 uuid 相同),而**构建产物**里 `assets/main/import/**.json` 那个节点的 `_components` 会是 `[null]` —— 三者一对,结论就没有第二种解释。
- **环上的颜色不要每 tick 重新盖一遍 —— 让每个格子跟着自己那一组走**(`ringOffset`)。这是目前为止最大的一刀,实测 tick 里 **`v127` 占 157 中的 127**(`c25` / `r0`),也就是一个 tick 里 **21.5ms** 花在整圈重绘上,每秒六次。
  **贵在哪**:`LoopSystem.step` 每 tick 把环旋转 **+1**,而且是**搬动**同一批 group 对象、不是重建。原来的映射是「格子 c ↔ 环槽 c」,于是**每个格子每 tick 都换一种颜色**;而换颜色就是 `MeshRenderer.material = ...`,它要重建 sub-model 的 pass、重排 instancing buffer。44 格 × 4 人、约四分之三会变色 —— 大约 **132 次材质赋值挤在一帧里**。
  **改法**:让 `ringOffset` 跟着环一起 +1,格子 c 画的是环槽 `(c + ringOffset) % capacity`。这样**格子跟着自己那一组走,颜色根本不变**;每 tick 变的只是它画在哪 —— 而那本来就每帧算一次(`repositionAll`)。重绘因此只剩 core 真正动过的那两格:门口清空的那一格,和入口填进来的那一格。
  **正确性不建立在「+1」这个假设上**,而是靠 `shownColor`/`shownCount` 逐格比对:万一 offset 错了,比对会照旧全量重绘,丢的只是这个优化,画面不会错。`update()` 的第三个参数 `rotated` 就是给初次绘制用的(那时还没人转过环)。
  连带要注意的:`playEntry` 拿到的 `channel.entry` 是**环槽**,必须经 `clusterOf()` 换成节点;`flierOwns` 存的也从环槽改成了**格子下标**。
  **实测结果(同一部真机、第 1 关、裸地 0)**:`40fps tick157 c25 v127 r0 max36` → **`51fps tick25 c24 v1 r0 max5`**。整圈重绘 **127 → 1 ms/s**,单个 tick 最长 **36ms → 5ms** —— **没有任何一个 tick 再大过一帧**,这正是「一顿一顿」消失的判据,而帧率只是顺带涨的。
  剩下的全在**每帧**那一侧了:51fps 里 tick 只占 0.5ms/帧,其余约 **19ms/帧**是场景本身。tick 里现在最大的一块反而是 `c`(core 逻辑)24 ms/s,合每个 tick 4ms —— 远在一帧以内,不值得动。
- **「跑一会儿帧率回不去」是手机降频,不是泄漏 —— 已经用重开关卡判掉了**。实测序列(第 1 关,裸地 0):X1 `40fps / 169ms/s / max36` → X2 `30 / 329 / 36` → X2 再跑一会 `26 / 360 / 40` → 切回 X1 `35 / 186 / 40` → **重开这一关 `35 / 186 / 41`**。重开会释放掉任何累积的东西,却**一点没恢复**,所以不是累积。
  第二个独立佐证在 tick 上:**同样的配置、同样的工作量,tick 从 169 涨到 186 ms/s** —— 活没变多,毫秒变多了,那只能是 CPU 变慢了。
  **代价:以后所有帧率数字只能在同一个热态下比。** 早先那次「40 → 50」的波动,现在知道有一部分就是这个,不是改动的效果。
- **真正的顿是「每个 tick 都是一个比一帧还大的疙瘩」,不是偶发尖峰**。`TICK` 是 0.17 秒,所以 X1 下是 **5.9 tick/秒**;169 ms/s ÷ 5.9 = **平均每个 tick 28.7ms**,而 max 只有 36 —— 平均和最大挨得这么近,说明**没有个别的坏 tick,是每一个都贵**。X2 也一样(329 ÷ 11.8 = 28.0)。
  一个 tick 是**跑在某一帧里面的**,所以那一帧至少 29ms —— 而 X1 的帧预算是 25ms。**每秒有大约 6 帧被撑成一帧半**,这就是「一顿一顿」的直接来源,和平均帧率是两回事。
  下一步不再推:构建标记把 tick 拆成三段打出来 —— `tick169 c40 v105 r24 max36`,`c` 是 `core.stepLoop()`、`v` 是 `loopView.update()`(整圈重绘)、`r` 是这个 tick 体里剩下的一切(HUD、座位数、上车、发车、解锁判定)。
- **人群不是每帧的瓶颈,这条是量出来的,而且和直觉相反**。把环上和通道里每组四个人换成**一个点**(`ROW_AS_DOT`),256 个人 → 54 个点、约 6.9 万三角形 → 3900,然后读两个速度下的帧率,按 `frame = P + tickWork / fps`(2 倍速把 tick 频率翻倍、不改变每帧工作量)把一帧拆成「每帧的」和「每 tick 的」两部分:

  | | 每帧 | 每秒的 tick 工作 |
  |---|---|---|
  | 256 个人 | 14.93ms | **254 ms/s** |
  | 54 个点 | 14.71ms | **147 ms/s** |

  **画这一群人每帧只要 0.2ms —— 等于不要钱。** 删掉 79% 的乘客几何一帧都没买到;买到的是 **107 ms/s 的 per-tick 工作**。两个结论:**再简化形象是白费的**;而这一切底下有一层约 **14.8ms(约 68fps)的地板**,那是场上其余的东西,跟乘客无关。
  **所以别再动几何了,该动的是 tick。** 构建标记因此多了一段 `tick NNNms/s max NN`(见 `tickFps`)—— 上面那两个数是从两个帧率**推**出来的,现在直接**量**。
  另外:**「2 倍速跑一会儿再切回 1 倍速回不到原来的帧率」这件事,在点的版本下同样存在**(58 → 48 → 50)。人群几乎删光了它还在,所以它不是人群。区分办法只有一个:**重开一关立刻看** —— 马上回到高值就是有东西在累积(泄漏),还是低值就是手机降频。
- **共用一个 mesh 不代表三角形是免费的 —— instancing 每个实例都要跑一遍顶点着色器**。乘客早就烧成一个共用 mesh、也已经 instanced,所以那份几何**只上传一次**;但铺满之后场上 **256 个人**,每帧就是把它**光栅化 256 遍**。原来 8/8/8 的分段是**一个人 464 个三角形、全场约 11.9 万**。这里原本的注释写着「这份顶点数是整个人群付一次,不是每个人付一次」—— 那句话对内存是真的,对帧是错的。
  分段数现在**按部位分开**,照各自在手机上实际占多少像素给(整个人约 40px):`HEAD_SEGMENTS` **6**(头最宽、又是环边缘的剪影,留得最多)、`BODY_SIDES` **6**(躯干只有约 7px,固定机位永远只看到正面)、`ARM_SIDES` **4**(胳膊半径 0.03 对 0.55 的人 —— 约 2px,方的和圆的分不出来,而两条胳膊改之前占了一个人**一半**的三角形)。**464 → 268,全场约 11.9 万 → 6.9 万。**
  **`CAPSULE_HEIGHT_SEGMENTS` 必须留在 8,这不是漏改 —— 8 就是下限。** 引擎把它按上下半球和圆柱各自占的高度比例 `Math.floor` 分配:胳膊的半球是 0.03 对 0.40 的长度,分到 `floor(hs * 0.136)` 圈,**hs 低于 8 就是 0**;为 0 时生成器算 `lat * PI / bottomSegments / 2` —— 0/0 —— 推入 **NaN 顶点**,而且一个球帽索引都不生成,**胳膊变成两头通的空管**。看着最像能省的旋钮,坏起来最不声不响。
- **「2 倍速更卡」不是帧的问题,是 per-tick 的问题 —— 而 per-tick 里藏着一次建节点**。速度按钮不改变每帧的工作量,所以 2 倍速掉得比帧率能解释的更多,只能是**按 tick 计的东西翻倍**了。找出来的是 `playEntry`:每个 tick、每条正在供给的通道,都**新建一整排四个乘客再销毁**(`makeRow` + `destroy`)—— 四个 Node 加四个 `MeshRenderer`,而 `MeshRenderer` 会带起一个 Model、一个 sub-model 和它的 descriptor set。这份开销**集中砸在一帧里**,所以它的表现是**顿**,不是平均帧率低。实测:铺满的环上 1 倍速 40fps、2 倍速 30fps。
  改成**每边一排、复用**(`flierRow`),整关就两排,进场之间隐藏。代价是**判据不能再用节点身份**:同一个节点被两个进场周期共用,所以「这个 flier 还是我的吗」变成了 `flierCycleId` 一个计数器,并且要额外记 `flierOwns`(这一边藏起来的是哪个 ring slot)—— 旧代码不需要它,因为被打断的那一次总是藏同一个 slot,而一旦两次进场共用一排,这就不成立了。
  `GameController` 的 `playBoarding` 仍然按次新建 flier,没动:上车要求门口有颜色对得上的车,不像进场那样每个 tick 都发生。
- **真机说卡,就把帧率打到屏幕上,别靠读代码推**(`tickFps`)。环被报"真机顿/模拟器好"已经两次,两次都只能从"每帧做了多少事"去推,而**帧率本身一直是个猜测** —— 上一次推对了一个原因(手臂频闪),但没人知道设备到底跑多少帧。现在构建标记那行末尾带 `· NNfps`,一秒刷一次,和标记、选关条一起属于临时开发件,一起删。
- **真机慢是「draw call 数」的问题,而 46 辆车曾经占掉其中 414 个**。每个车模是 **9 个 primitive**,也就是 9 个 `MeshRenderer`;一关 46 辆 = **414 次独立绘制**,而全场大概 600 次。18fps = 每帧 55ms,按手机端一次 draw call 约 80µs 算,460 次就是 37ms —— 数量级正好对上。
  **46 份同样的 9 个 mesh 是 instancing 的教科书场景**,但它只有在**材质也是 instanced** 的时候才成立。所以 `recolorCar` 现在把**每一个材质槽**都换成 `instancedLitMaterial`,包括那五个没人重上色的角色(trim / lamp / taillamp / tire / hub)—— 不换的话它们各自还是一次非批次绘制。
  **换掉它们不损失任何东西,而这是关于这三个模型的事实,不是假设**:`bus/car/truck.glb` 的**贴图数和图片数都是 0**,七个材质全是一个 flat `baseColorFactor`。哪天模型带贴图重导出了,这条要重新审 —— `readMainColor` 会把贴图静默拍平成一个颜色。
  实测口径:**车 414 → 约 45,阴影 46 → 约 1,全场约 464 → 约 50。**
- **这条路的完整实测阶梯(同一部真机、同一关)**:**8fps → 18fps**(去 post-process + 乘客烧成一个 mesh)**→ 40~52fps**(车与阴影 instanced)。同一帧模拟器 49 → 59。
  最后那一档是个**区间而不是一个数**:同一份构建、同一关先读到 40、后读到 52,中间一行代码没改。**所以单次读数的浮动就有 ±10**(升温、前几秒、GC),判断一次优化有没有效要看跑一会儿之后的稳定值,别拿两个单次数字相减。
  两个结论值得记住:**「draw call 数」的模型被验证了**(估 464→50 对上了 55ms→25ms);而 40 之后 **draw call 已不再是瓶颈**(约 50 次 × 80µs ≈ 4ms,占 25ms 帧的不到二成)——再往下挖就不能再抽提交次数了,要先在真机调试里分开看 **GPU 占用 / JS 耗时 / 顶点数**。
  下一个最大的候选项是**乘客的面数**:环上 112 人 + 通道 80 人 = **192 个人**,每个是 1 个 `SPHERE_SEGMENTS=8` 的球 + 3 个 `CAPSULE_SIDES=8` 的胶囊。它们已经只有约 4 次 draw call,所以现在花的是**顶点**而不是提交——要砍只能砍分段数(会看得出来)或砍人数(环长 28→24),两者都是**能看见的取舍**,先测再砍。
- **`blobShadow` 曾经给每辆车现建一个 mesh**。几何完全一样,大小差异在**节点 scale** 上 —— 所以每辆车一个 mesh 从来没表达过任何东西,却让 46 个阴影**永远无法批次**,还要把同一个圆盘上传 46 次。现在圆盘建一次共用,材质也加上 `USE_INSTANCING`。透明物的绘制顺序在这里无所谓:它们都是贴在板面上同一种深色椭圆,没有两个会以顺序看得出差别的方式重叠。
- **`roundedSprite` 曾经画的是椭圆,不是圆角矩形 —— 因为 9 宫格的 inset 从来没设过**。`frameFrom` 只设了 `rect`/`originalSize`,`insetLeft/Right/Top/Bottom` 全是 0;而 SLICED 精灵没有边框可保护时,**整张贴图就是"中间格",直接被拉伸到节点尺寸**。那张贴图是 32px、半径 15 —— 基本就是个圆。所以 HUD 上每一块"圆角矩形"其实是**那个圆被拉成的椭圆**。210×88 的小药丸上这看着像圆角药丸,没人多看一眼;520×380 的对话框上它是一坨白斑,这才暴露。修好之后半径必须变成**参数**:88 高的药丸和 430 高的面板不可能共用一个半径。默认取短边一半(即胶囊),原有的药丸因此外观不变。
- **停车场没有格子**。车是**连续坐标 + 朝向角**(`CarSpec` 的 `x`/`y`/`angle`,度,0° = +X 逆时针),碰撞体是有向矩形,判定在 `core/geometry.ts`。板坐标原点在场地中心、**+Y 朝上**,1 板单位 = 老网格的格距 0.7533 世界单位 —— 相机取景和地板因此在自由角度改造中一行没动。
- **相机必须是正交的,这不是审美问题**。玩法是纯 2D,core 判定的是车在板面上的 footprint;但车是**立在**板面上画的,车顶离相机近 `hgt`(见 `buildCar`)。透视相机会把车顶按 `d/(d−hgt)` 放大并沿径向往外推 —— 而停车场中心在 y = −2.73、相机轴在 y = 0,整场偏轴,场地底部离轴约 5 个单位。实测十关:车顶落点离 core 所算的 footprint **中位数差 0.109 板单位、最大 0.187**,而 `CLEARANCE` 只有 0.04。画面撒的谎是整个间距预算的 2~5 倍,一次坏三样:**挡路判定**(用 core 自己的扫掠跑投影后的盒子,360 辆里 13 辆与 core 不一致,其中 10 辆是「core 说能走、眼睛看是被挡」)、**尺寸档次**(看到的是车顶加透视露出的侧壁,越偏轴露得越多 —— 两辆同为 `medium`、同模型同 `CAP_BOX` 行的车,宽度能差 26%,73 辆 medium 里 34 辆画得比某些 big 还宽)、以及**点击拾取**(`onTap` 把射线打在板面、`pickCar` 测的是 footprint,而玩家瞄的是没盖在盒子上的车顶)。正交之后,车无论多高、停在哪里都精确投影到自己的 footprint —— 在场内、在环道上、停进车位时都成立。`orthoHeight` 取的就是原来 45° 垂直 fov **在板面上**的半高,所以 z = 0 的取景一像素没动,别的东西至多挪回它原本被放大的那 2.4%。**要把透视放回去,就得先让 core 也认识车顶那个平面。**
- **补间动画的回弹目标必须是「静止姿态」,不能是「当前值」**。`squash` 原本用 `body.scale.clone()` 当回弹终点 —— 而一次被拒绝的点击会对同一个 body 压两次(`onTap` 一次,`playShake` 撞上障碍时再一次),第二次落在第一次里面的概率是 **99.2%**(nudge 段下限 0.12s,而这个补间要 0.18s,被挡的车 gap 中位数只有 0.01 板单位)。于是第二次把**动画中途**的缩放当成了静止姿态,而且**逐次累积**:拒绝一次 (0.987, 1.018),十次长宽比偏 36%,二十次偏 85%。被挡的车恰恰是玩家反复点的车 —— 这就是「同一种车尺寸不一样」的来源,也让车身画得比 core 认为的宽出近两成、看着像压进了旁边的车道。现在 `squash` 用 WeakMap 记住首次的静止缩放,并在开始前按 tag 停掉仍在跑的那一个。**同一个节点上叠补间,就得先停旧的、并回到已知姿态。**
- **场景的天空盒关着,envmap 引用是清空的 —— 别让编辑器把它加回来**。相机是 `SOLID_COLOR` 清屏(见 `setupCamera`),天空盒**从来不会被画出来**;而 `SkyboxInfo._envLightingType` 是 `0`(半球漫反射),光照来自 `AmbientInfo` 的 skyColor / groundAlbedo,**跟 envmap 无关**。但 Cocos 只要场景里还引用着那两张 cubemap 就会把它们打进包:实测微信构建里是 **12 个 png、约 808KB**,占了 `assets/main` 那 958KB 的绝大部分 —— 全是喂给一个不渲染的天空盒的。所以 `_enabled` 是 `false` 且三个 `_envmap*` 字段都是 `null`。在 Inspector 里手滑重新勾上 Skybox,这 808KB 会立刻回来。
- **不要展开 Map / Set 的迭代器,用 `Array.from`**。`[...map.keys()]` 这种写法**在微信小游戏构建里不成立**,而且**静默失效**。第 1 关在微信里一开局 `state=deadlock`,而同一份数据在 node 和手机浏览器里都正常:场上 36 辆车都在、几何精确(`CAR_SCALE` 1、`CAP_BOX` 完好、无 NaN、把普通数组喂给 `firstBlocker` 时 22 辆被挡 14 辆通),但 `movableCarIds()` 返回空 —— 空的 key 列表 filter 完什么都不剩、`canExit` 一次都没被调用,所以**不抛异常**,只是变成一个「谁都动不了」的场地,而 `isDeadlocked()` 如实地把它读成死局。
  当时全项目**只有 `lot-system.ts` 那两行**在展开 Map 迭代器,而**正好就是坏掉的那两个函数**;其他所有从 Map 建数组的地方本来就走 `Array.from`,在同一个构建里全部正常。(core 里另一处展开是 `level-data.ts` 对 `Object.keys()` —— 普通数组,数组迭代是好的。)
- **微信预览会把旧资源发到真机上,而模拟器不会 —— 开 MD5 缓存**。实例:构建目录里第 1 关是四色,模拟器画四色,**真机上同一份代码画两色**。模拟器直接读本地 `game/build/wechatgame` 目录,真机拿的是**上传上去的那份包** —— 上传是按文件增量的,一条陈旧记录就能让某个资源永远不被重传。
  **根治办法是构建面板里勾上 MD5 缓存**(本项目曾是 `md5Cache: false`)。开了之后每个资源文件名里带内容哈希,改了内容就是一个**新文件名**,增量上传根本无从命中旧字节。应急办法是开发者工具 **工具 → 清缓存 → 全部清除**(清的是**工具侧**的上传缓存,手机侧删多少次都没用),或改用**真机调试**(推完整包)。

  **开了 MD5 缓存的 Cocos 是先写原名、再改名成带哈希的**(资源那次日志里连 `unlink` 都留下了)。开发者工具的**文件监听**把这两个名字**都**排进了编译队列,而改名前那个在编译/预览真正跑到它时早就不存在了 —— 于是 ENOENT。这跟"清单陈旧"没关系:两次事故的日志都显示项目是在构建**之前**打开的(10:35:59 开、10:36:28 构建;10:49:30 开、10:50:08 构建),队列里的幽灵是**这一次构建**刚制造出来的。
  也别指望它只砸代码文件:见过的三例分别是 `index.<哈希>.js`、`src/import-map.js`、以及 `af521bc2-….json`(那是 `resources/audio/board.wav` 的 import json)。一次构建里没带哈希的 `onFileChange add` 有 **80** 条,随便哪一条都可能被抽中。
  **正确顺序是:开发者工具关掉项目 → 在 Cocos 里构建 → 再打开项目 → 预览。** 重新打开会重新枚举目录,幽灵队列随之清空。
- **MD5 缓存本身仍然要开,它治的是另一个病**:上传是按文件增量的,一条陈旧记录能让某个资源永远不被重传(四色画成两色),而内容哈希让增量上传无从命中旧字节。它和上面那条 ENOENT 是**两回事**,只是恰好都在开了 MD5 之后才看得见。
  **诊断它需要屏幕上有版本信息,否则无法区分“旧包”和“新包画错了”。** 这一次花了四轮:新旧两版第 1 关**除颜色字符串外逐字节相同**(36 辆车位置/角度/车型一致,乘客数都是 744),而旧数据刷 `红蓝红蓝`、新数据刷 `红蓝绿黄`,所以**一个丢掉了绿和黄的渲染器,画出来正好就是旧数据的样子** —— 两种解释在像素层面完全一致。最终定案的是 `GameController` 里那行**构建标记 + 实际加载到的数据指纹 + 资源 uuid**:同 uuid、同代码、不同内容,只能是分发。
- **微信构建的 `Enable Wasm Brotli Compression` 必须关着**。开着它,同一份包在微信开发者工具里预览正常,**真机上卡在 Cocos 闪屏**;关掉之后,真机 1.9 秒就走到 `[Game] level 'level-1' started, state=playing`。这两件事是量到的。机制是**推断**:车模型是 meshopt 压缩的(`tools/reduce-model.mjs`),解码器是一个 wasm 模块,Brotli 把它变成 `.wasm.br`,真机上取不回来。
  
  **注意 `GameController` 里那三段 8 秒兜底救不了这一类卡死。** 兜底跑在控制器里,而真机调试的日志显示,Brotli 打开时连 `[Game] controller start` 都不出现 —— 卡的位置在引擎自己的引导阶段,比场景实例化和我们的任何脚本都早。所以那行 marker 的用处不是修复,是**分流**:它在,说明卡在我们的预加载链里,后面会有具名的超时警告;它不在,问题在引擎或资源层,别在 `GameController` 里找。
- **版面常量必须从实际取景推导,不能写死**(`viewFrame` / `fitCamera` / `buildBoard`)。正交相机的**竖直**半视野是固定的 `VIEW_HALF_H`(6.213),**横向随宽高比而变** —— 之前的透视相机 `_fovAxis` 是 VERTICAL,行为完全一样。而本文件里所有取景常量,都是按编辑器预览窗那个 **约 0.79** 的宽高比选的。竖屏手机只有 **0.46**。
  预览窗的可视框是 **±4.90 × ±6.21**,1170×2532 手机是 **±4.67 × ±10.11** —— **更窄而且高得多**。所以写死的 `RING_LOW`(-5.76)和 `LOT_HALF_W`(3.83)**两个方向同时错**:环道外沿落在 4.90,在 4.67 宽的视野里被裁掉;而停车场仍然按 6.21 半高在算尺寸,4.5 个单位的竖向预算白放着。现在两者都从 `viewFrame()` 推导,相机又按**实际画出来的东西**对齐(`needHalfW` / `needHalfH` / `camY`),所以后续改窗只会拉远,不会裁掉东西。
  取景宽度用的是 **`LANE.edgeLimit`(4.67),不是本关实测的通道伸出量**。它是 core 已经声明、`validateTrack` 已经在把关的上界,对每一关都是同一个数 —— 这就是重点。十关自己的伸出量在 **3.08~4.36** 之间(lookahead 是难度旋钮,所以逐关不同),按关精确 fit 会让整个板面**逐关缩放不一样**,而停车场十关同尺寸 —— 这个仓库已经因为「同种东西大小不一」被报过一次 bug 了。
- **收種取景宽度会让车变小,不是变大 —— 已量过,不要再试**。直觉是「镜头拉近 → 东西变大」,但把取景从 4.67 收到实测最大伸出量 4.36 之后,车小了 **7.4%**,停车场占屏宽从 **82% 掍到 75%**。原因:环道占的是**固定的世界宽度**(每边 `RING_OFF + ROAD_H/2` = 1.07),镜头拉近之后它就吃掉更大比例的屏幕。
- **板面的尺寸由宽度完全决定,竖向富余对车的大小一点贡献都没有**。正交相机下 `orthoHeight = needHalfW / aspect`,世界→屏幕的缩放比只由 `needHalfW` 和屏宽决定。所以「上下空白多」和「车太小」其实是**同一件事的两面**:板面太宽太扁。把各段拉开只能把空白挤掉,不能让车变大;真正能交换的只有**停车场自己的长宽比**。所以 `LOT` 先从 9×6 改成了 **7×8 竖的** —— 面积几乎不变(56 vs 54),但手机上车大 **31%**、空白从 **42% 降到 23%**。
  **而宽度方向反过来:既然 cell 由高度卡住,把停车场加宽是免费的。** 现在是 **8×8**,而这个 8 是量出来的拟合值不是整数:手机上高度预算给出 cell 1.032、宽度预算给出 1.0325,所以宽到 8 为止车的尺寸一点不变。宽到 8 后车的占地 8.416 对应底板 8.720——差的恰好是底板自己的 0.3 边框;7 的时候车只占 7.364,左右各空出 0.37 的裸沥青 —— 那就是“停车场没占满”看起来的样子。
  **两个地方要同时改,否则改动会自我抵消。** 一是 `needHalfW` 不能再把环道算进去(`max(LANE.edgeLimit, lotW/2)`,不是 `+ RING_OFF`)—— 否则底板一宽,相机就为了容下一条**故意半出屏**的侧道而拉远,每辆车反而变小(就是上一条反着跑)。二是 **车数必须跟上**:停车场大了 14% 而车数不变,只会比以前更空。所以 `CARS_PER_LEVEL` 36 → 46,密度 0.643 → **0.719 辆/单位²**,车体覆盖率 0.452 → **0.508**。
- **编辑器预览窗必须设成手机分辨率,否则看到的不是游戏**。`LOT` 竖过来之后,它在 0.79 宽高比下是**高度受限**的:车比以前小 **25%**,而且 slab 会被 `Math.max(lotWidth(...), 2 * lotHalfW)` 撑得比车需要的宽很多(预览 7.68 对 4.26),看起来就像坏了。把预览设成 1170×2532 之后两边就一致了。
- **停车带能覆盖全部颜色的关卡,在数学上不可能卡住** —— 所以**难度要求「颜色数 > 已解锁车位数」**。推导:覆盖全色 → 到闸口的每一排都能上车 → 每一 tick 都有环道格子腾空 → 环道永远封不死,而**环道封死是唯一的输法**(`LoopSystem.reachableColors` / `GameCore.isDeadlocked`)。实测佐证:四种不同停车场布局 × 每种 66 种上色,能打败一行规则的上色数量在 **4 色时是 0/66(四个布局全是 0)**、5 色时 0~2、6 色时 4~7。**四色不是搜不到,是空集。** 所以第 1~2 关(4 色)是教学关,这是曲线决定而不是生成失败。
- **量难度不能只用“乱点”策略 —— 玩家用的是一行规则**。这条是一个**已经犯过一次的错**:上一版拿“乱点”(每 tick 把能动的车随便塞满空位)量出“颜色数就是难度”,据此把曲线陡到 2/3/3/4/4/5/5/6/6/6 并声称修好了。实际上玩家用的是**“保持四个车位颜色互不相同”这一句话**,而它把**那十关全部赢下来了**,包括 6 色的关卡。底线策略选错,量出来的数字再真也是在答错题。现在的验收在 `core/play-sim.ts`:**`keepDistinct` 必须输且 `careful` 必须赢**,两半缺一不可 —— 只前者失败是“关卡自己会玩”,只后者失败是“无解”。
  **验收策略只能看玩家看得见的东西** —— 环道上的排,加每条通道前 `lookahead` 排,就是 `TrackView` 画出来的那些。用一个能读完整队列的策略去证明“这关能过”,等于把公平性交给一个开天眼的玩家 —— 比不检查更坏,因为它会发出一批“看上去不公平、而原因玩家永远发现不了”的关卡。
- **按出场顺序轮流上色 = 把答案发给玩家**。`scatter` 里 `PALETTE[i % colors]` 的 `i` 是 `peel()` 算出的**能开出去的顺序**,所以停车场最外层永远恰好凑齐每种颜色各一辆 —— 实测第 6~10 关**没有任何一拍**是“找不到新颜色”的。它现在只是 `choosePainting` 的**搜索起点和兜底**。重新上色是**免费**的:乘客队列由车**推导**而来(`queueFor`),所以任何一种上色天然颜色平衡、不可能违反 `validateLevel`,而停车场几何(blocked / rounds 那条曲线)一点不动。
  成块上色是**悬崖而不是旋钮**:6 色下块长 4 正好是“一行规则输、认真玩赢”,块长 6 就变成**谁都赢不了**(被迫连停四辆同色)。所以块长只是开局几手,后面靠带种子的随机上色 + 模拟对局验收,**不能手调**。
- **可解锁的车位算作“还有位子”,不能判死局**(`isDeadlocked`)。停车带满了、但还有锁着的位子 —— 玩家可以免费点开一个,那就**还有合法的下一步**,判死局等于提前结束一局玩家本来能继续的关。这也是这个机制的全部形状:**解锁的位子越多,关卡越难输**。而它的尽头是一个**必胜键**:7 个车位 ≥ 6 种颜色,全开之后停车带覆盖了所有颜色,上一条定律直接适用。实测:一个乱点的玩家只要卡住就点解锁,**十关全胜、任何初始车位数下全胜**。这是一个**有意保留的商业选择**(激励视频的价值恰恰来自它很强),代价是难度的**基准线必须是“不解锁”** —— `simulate` 因此把 `slots` 夹到 `unlocked`。
  `ParkingSystem.parked.length` **就是**已解锁数(数组按 `unlocked` 长度建,不是 `slots`),所以解锁 = 末尾 push 一个空位,**现有下标连同它们的车和 `seq` 全部不变**(上客顺序依赖这个)。也因为如此,**只能按顺序解锁**,而视图里也只有“下一个”那个位子可点、只有它带三角标 —— 把按钮画在其他位子上会承诺一个点下去不会发生的事。
- **"卡住"和"输了"是两件事,而画面上长得一模一样 —— 必须分别说出来**(`GameCore.needsUnlock`)。停车带满了、上面没有一辆车还能上人(颜色到不了闸口),但**还有锁着的位子** —— core 判定这不是死局,而且它是对的:开一个位子是合法的一步,开完关卡继续。问题在于**没人告诉玩家**:转盘照转,`剩余乘客`再也不动,屏幕上什么都不变。实测**一个舍不得用解锁的玩家,十关 80 局里有 59 局停在这个状态**(第 6 关 8/8),而游戏一声不吭。玩家的原话是"当前已经失败了,没有判定失败" —— 它没有失败,它是**哑了**。
  现在这个状态会**弹一个模态框问你**:开一个位子,关卡继续;关掉它,**这一关就判负**(`declineUnlock`)。这是**唯一一条**"局面里还有合法着法却结束关卡"的路径,所以 `declineUnlock` **自己复查 `needsUnlock()`**,不信调用方 —— 弹框弹出到手指落下之间可能有辆车刚停好,局面又活了,那一下就不能算数(而且重复点关闭必须幂等)。
  `needsUnlock` 和死局共用 `canFill()`,所以两者对"没有车能上人"的判断不可能分歧;而两者**互斥** —— 一个请你行动,一个宣告结束。
  **注意锁上原本就有的那个播放三角不算数**:它是 affordance,停车带运转正常时长得一模一样,不构成"现在只剩这一步"的信号。模态框吃掉**所有**点击(包括选关条),因为一个能靠点别处躲开的问题就不是必答题。
- **上客按“到达顺序”选车,不能按车位下标**(`ParkedCar.seq` / `findMatchingSlot`)。车位下标**不是**到达顺序:`park` 永远取最小的空位,而位子会在车开走后被**重复使用** —— 几轮下来,停车带上**最老的车可能坐在最高的位子里**。按下标选就会把它**抛弃**:它抱着已经上车的乘客无限等待,而位子更低的新车把人全拿走。第 1 关实例:两辆红车,老的还缺 12 个人,新的（在 0 号位）已经上了 12 个 —— **两辆半满的同色车也是更差的谜题**,因为谁都快不了。
  **`seq` 必须在“到位”时发,不能在“点击”时发**。这是同一个 bug 的**第二条路**:`park` 在点击时发号,但车要开到位才能上人,而开到位的顺序取决于**路线长度**（车在停车场哪个位置、去第几个车位）—— 两个顺序会不一致。先点 A 再点 B、但 B 先到位:B 上了一排(4 人),然后 A 到位、拿着“点得早”的号把优先权抢回去,**B 就抱着 4 个人被抛在那里** —— 和按下标选车是完全同一个终点,只是绕了 `ready` 这条路。所以 `setReady` 在**false→true 的边沿**重新发一个 `seq`,**只在边沿上**—— 对已经 ready 的车再调一次不能把它排到队尾,那恰好又把它抛弃一次。
  两条规则合起来给出真正要守的不变量:**每种颜色最多一辆半满的车**。唯一的例外是一排人拆到两辆同色车上,而它在同一 tick 内就消失 —— 被填满的那辆在同一次 `removeFull` 里就开走了。
- **车位尺寸必须从“最长的车”推导,不能写死 —— 否则大小关系会反转**(`stallFootprint`)。车位曾经是写死的 0.78×1.06 世界单位,而大巴在板面尺度下长 1.92 —— `stallScale` 为了把它塞进 1.06 深的位子里,**整体缩到 0.563**,宽度跟着一起缩;而小车本来就够短,被 `min(1, ...)` 拦在 1,保住原尺寸。结果是**大巴停进去比旁边的小车还窄**(0.344 对 0.464,窄 26%)—— 游戏里最大的车成了车位里最细的东西。
  这个反转**一直存在**(老板面尺度下是 3%,看不出来),停车场竖过来之后场上的车大了 31%、车位没变,3% 就变成了 26%。现在依赖方向反过来:**车位 = 最长车身（`CAP_BOX.big`）× 余量 × 板面尺度**,停车带直接坐在环道上面,环道轨道（`LOOP_Y`）再被顶上去让开。于是三种车的 `stallScale` 全部是 **1** —— **你点的那辆车就是停进去的那辆车**。
  代价说清楚:**小车只能填满不到一半的位深**。绕不过去 —— 任何车都可以停进任何位,所以位子必须能装下最长的那辆。`STALL_FILL_W`/`STALL_FILL_H` 留着当**上限**(目前分别还剩 7% 和 13% 余量),那点余量就是模型重导出后比例漂一点而不至于又开始缩车的余地;`stallScale` 也留着,它是 `CAP_BOX` 漂掉之后唯一阻止车直接画到邻车身上的东西。
- **`CLEARANCE`(0.04 板单位)管的是「停着的车」,不管「开动的车」**。它用在三处:`packBox`、`validateLevel` 的两两校验、`pickCar` 的点击放宽。**车道判定(`firstBlocker`)扫的是未膨胀的车身** —— 车身不碰就让走,余量再细也让走。它取的是格子时代**最紧**的那个间隙(小车头尾 `1 − 0.964 = 0.036`),不是平均值。

  **这个分工是量出来之后定的。** 车道也要这个余量时,250 辆被挡车里有 18 辆其实挤得过去,被拒绝的最宽真实空隙是 **2.7 px** —— 这个边界细到看不见,所以卡在它附近的车全都「看着能过却过不去」。反方向的代价很小,而且**恰恰是因为打包仍然强制这个余量**:停着的车两两至少一个 `CLEARANCE`,所以大多数通道本来就够宽,改完之后 114 辆能走的车里只有 4 辆贴到 1.3 px 以内,最紧 0.5 px。

  **凡是要用这个余量的地方,都必须「一对各分一半」。这不是写法问题,是正确性问题。** 把整个间距堆在一辆车上、另一辆不膨胀,在可以旋转的矩形上是**另一条规则**:矩形膨胀 `d` 后在轴 `n` 上的投影半径增加 `d·(|n·u| + |n·v|)` —— 正对时是 `d`,45° 时是 `d√2`。所以整份堆在一辆上最多能到 `√2·CLEARANCE`,而两边各半最少只有 `CLEARANCE`。**格子时代所有车轴对齐,两者恒等,谁也没发现;自由角度一来立刻分家。** 后果是 `validateLevel` 判合法的一对,在 `firstBlocker` 里却重叠 —— 而 `sweepHit` 对已重叠的盒子**无论朝哪个方向都返回 0**,于是车被判「被身后的车挡住」。十关 360 辆里有 15 辆中招,15 辆全部是 gap 恰好为 0、挡路车偏离车头 128°~159°。**再加一个读 `CLEARANCE` 的地方,就分一半。**
- **`firstBlocker` 只在满足 `CLEARANCE` 的场地上才有意义**。膨胀后的车一旦与邻车重叠,`sweepHit` 无论朝哪个方向都返回 0 —— 于是排得过密的一整列车全部报"被挡",连最前面那辆也是,而且报出来的 blocker 可能在**后面**。是 `validateLevel` 的三条几何规则让它成立的。
- **`CAP_BOX`(`core/types.ts`)是车身尺寸的唯一事实**,view 反过来按它缩放模型。这是主从倒置 —— 以前是模型 AABB 去适配格子、尺寸算出来。**别再从模型反推 `CAP_BOX`**,会绕成一个圈。
- **换车辆模型之后先跑 `node tools/check-car-models.mjs`**。模型的**绝对尺寸无所谓**(每档车各自算一个 `s`,画出来必然是 `CAP_BOX × 格距`),有所谓的是**长宽比**:`s` 取两轴的 `min`,比例一漂,一个轴顶住、另一个轴就填不满 —— 车填不满 packer 给它留的位置,缝就出现在那里。core 读不了 `.glb`,所以这个脚本是唯一能发现 `CAP_BOX` 与模型脱节的东西,而失效方式是**静默且不对称的**:模型变大反而让车和点击判定一起**变小**。零依赖,超差以非零码退出,并直接给出该填的数值。
- **`pack` 用分离松弛,不是拒绝采样**,而且它**不保证收敛** —— 收不敛就返回空数组让 `generateLevel` 换下一次尝试。信不信它的输出,由 `validateLevel` 的三条几何规则说了算。
- **`packBox` 比 `validateLevel` 多留 `ROUND_MARGIN`(1.5e-4)**。松弛的不动点是"两两几乎相切",而 `scatter` 之后把坐标舍到四位小数,能让相切的一对再靠近约 1.4e-4 —— 少了这点余量,86% 的满员尝试会被自己的校验丢掉,难度搜索的有效样本从 200 次掉到 2~5 次。
- **剥离时每辆车只有 `angle` 和 `angle + 180` 两个朝向可选**。矩形在半周旋转下与自身重合,所以摆位定了、朝向还能二选一 —— 这也是 `peel` 与 `isSolvable` 的占用模型完全一致的原因。
- **场地的面积占用率约 45%(逐关 41.7%~50.0%),不是格子时代注释里的 88%**。后者数的是"占了多少格",差额正是方格里塞长条车时四周那圈空气。逐关波动是因为每辆车的档位是独立抽样,36 次抽样的车型组合本身就有几个百分点的方差。
- **难度曲线的 blocked 区间是量出来的,不是定出来的**(`BLOCKED_FIRST`/`BLOCKED_LAST`)。斜向通道是斜的扫掠带,蹭到的车比正交多,分布整体上移。**但这个测量有两层循环要绕开**:一是读十个已发布关卡的 `blocked`,报的只是"搜索在旧目标下找到了什么";二是就算换到目标不动的那段(id 11 以后曲线是平的),生成器**只接受落在旧容差窗口内的候选**,所以观测到的上下端(24 和 30)是**窗口的边,不是几何的边**。窗口内部的形状是可信的(取第一个命中,窗口内无偏),下限 21 也是可信的(它来自 id 1~10,那几关的旧窗口一直探到 15、没被截断)。上限则不知道。
- **`routeToSlot` 的第一段开到环道,不是开到停车场边缘**。停在边缘意味着车**中心**刚跨过边界、车身还有一半在场内,下一段原地转向就会把车尾扫过旁边还停着的车 —— 实测 360 辆里有 221 辆穿模。开到环道则是 0 辆,而且大多数车的第二段变成零长度被 `driveRoute` 丢掉,回到改造前那种一段式出场。
- **侧向车道和停车场的重叠是取景逼出来的,只能选它怎么读**(`DRIVE_LIFT`)。侧道在 `driveSideX` = 4.28,最外层停着的车伸到 4.19,车宽 0.65 —— 重叠 0.23。而**没有一个位置能两全**:画面半宽 4.67,车外侧只剩 0.48 的空当。(把车道退回画出来的 4.98,车身只剩 0.016 在屏内,那是上一版的状态。)既然躲不掉,剩下的问题就是**同深度相交**还是**干净遮挡**:抬高 1.2 之后,开动的车像走在一条离观众更近的路上,从停着的车前面过去。正交相机,所以这一抬在屏幕上是零成本的。出场那一段抬升不会压到别人 —— core 只放行走廊为空的点击,那条路按定义是空的。
- **一次到位的时间由「整条路线」定速,不是每段**(`driveTiming`)。路线长短取决于车停在哪、抽到哪个位子,固定速度下这个等待差**五倍**,而长的那些正是看着像卡住的。实测十关 1840 条车/位路线:原来 **中位数 2.14s、最长 3.93s,57% 超过两秒**;现在 **0.53 / 1.30 / 1.76s**。速度上限 `DRIVE_SPEED_MAX_MULT` 是让远处的车还像车 —— 不封顶的话最长那条要跑到 28 单位每秒,基准才 14。
  **不要改成每段一个固定时长**:环道各段长度能差十倍,那样读起来是车在每个拐角换挡(见 `driveRoute`)。
  另外 `finalApproach` 那个「停进位子时改尺寸」的补间必须**等于最后一段的时长**,而最后一段的时长现在随速度变 —— 所以 `driveTiming` 把它一并算出来返回。写死 0.28 的话,车早停好了还在变大。
- **一辆车停进车位时只会变小,不会变大**(`stallScale` 对 1 取 `min`)。车位比车长,不加这个上限的话小车停进去会凭空放大。
- **地面导引线试过,拆了 —— 别当成没做过的好主意**。spec 第四节为「斜向遮挡读不懂」预留的方案就是给每辆车画一条地面导引线,做出来了(每车一条渐细、着车身色、画到场地边缘),**实测太密**:一场 36 条线交叉起来接近一张铁丝网,反而更难读。已移除。要重做的话,先想清楚怎么解决「同屏 36 条」这个密度问题,而不是重走一遍。
  它想解决的那个现象是真的,而且量过:十关 250 辆被挡车里,**45 辆(18%)面前有超过 20 px 真正空着的路**,29 辆超过 33 px,最极端的一辆面前空着 120 px、挡路的车在 185 px 外。所以玩家说「看着能过」时,**对近处的判断是准确的** —— 眼睛做不到的是顺着一条斜线追那么远。现在扛这一条的**只有**车道判定改成了「车身不碰就让走」(见上,把那 18 辆真能挤过去的放行了)。**指认挡路车的东西一件都没有了** —— 地面导引线和挡路车黄框都试过、都因为观感被拆掉,而 `flash` 做不到这件事(见下一条)。所以被拒绝的点击现在只说「不行」,不说「是谁」;剩下的线索只有顶推动画朝哪个方向撞过去。要重开这个话题,先读那两次为什么被拆。
- **`setEmissive` 不能用来「指认某一辆车」**。`litMaterial` 是**按颜色缓存**的,`recolorCar` 把同一个 Material 实例赋给所有同色车;而 `setEmissive` 是 `mat.setProperty('emissive', ...)` —— 原地改那个共享材质。所以 `flash(挡路车)` 会点亮**每一辆同色车**:第 1 关两种颜色、36 辆车,一次亮十八辆。`materials.ts` 里把这个原地修改判断为「至多是外观问题」—— 当发光只是装饰时确实如此,**但当发光是「谁挡了我」的唯一答案时,它就是全部的 bug**。指认单独一辆车只能用**几何**(自己的节点、自己的网格,挂在 body 下所以跟着车头转),不能用材质属性 —— 这样做过一版(`blockerRing`,黄框),因为观感拆掉了。哪天要再做,记住入口不是 `flash`。
- **别再把间距余量加回车道判定里**。曾经加过,量出来的结果见上一条。也别想着靠生成器筛掉边缘情况:正确的条件是「任意在车道上的有序对都不能是边缘的」(阻挡关系会随着车被开走而改变,所以只保证开局没用),而即使只要求 2 px 余量,每关也有 8~18 个边缘有序对、全场 3683 个有序对 —— 要求归零等于毙掉所有候选。**解法是车道判定只问车身碰不碰**(见上一条)。
- **`pickCar` 在车自己的坐标系里做盒判定**,并额外放宽半个 `CLEARANCE`。轴对齐的盒子对斜停的车能宽出四成,点旁边的空角会点中它;而放宽半个间隙是**可证明安全**的上限 —— core 保证任意两车身间隔一整个 `CLEARANCE`,所以两个放宽后的盒子仍不可能同时包含一个点,"第一个命中"依然无歧义。要更大的点击面积,就得改成"取最近的车"而不是"取第一个包含的车"。
