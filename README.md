# 挪车接客(parking)

一款微信小游戏方向的单机休闲解谜游戏,**双层复合玩法**:

- **下半屏**:挪车谜题(类 Parking Jam)。停满带箭头的车,点一下车就沿箭头直线开出;被挡住就开不出去,只会抖一下。开出的车停进上方的车位。
- **上半屏**:传送带式接客。彩色乘客站在一条循环轨道上绕圈走,走到轨道底部的**上车口**时,如果某个车位上停着**同色且未满**的车,这一组乘客就上车。车坐满自动开走,腾出车位。

**过关**:乘客池空 + 轨道上没人 + 车位全空 + 网格无车。
**死局**:车位全满、没有一辆车还能坐满、网格里也没有一辆车能开出去 —— 此时判负。

引擎 Cocos Creator **3.8.7**。当前有 10 个离线生成的关卡,每关 36 辆车。

---

## 目录结构

```
game/                 Cocos Creator 工程(用 Creator 打开这个目录)
  assets/main.scene   唯一场景
  assets/scripts/
    core/             纯逻辑层:不 import 'cc',可脱离引擎单测
    view/             表现层:import 'cc',负责建模、动画、HUD、相机
  assets/resources/levels/level-N.json   离线生成的关卡数据
logic/                核心层的测试与构建入口(jest + tsc 配置)
tools/                离线脚本:关卡生成、音效生成、模型减面、车辆模型体检
editor/               本地关卡编辑器(esbuild + 一个 node 静态服务)
docs/superpowers/     设计文档(specs/)与实施计划(plans/)
```

### 最重要的一条约定:core 不认识 Cocos

`core/` 里的任何文件都**不能** `import ... from 'cc'`。这是整个测试体系的地基 —— 一旦引入,jest 就再也加载不了这个文件,那条逻辑从此只能靠肉眼在编辑器里看。

因此分工是:

- **core 管拓扑**:谁挡住谁、哪一组乘客下一拍到上车口、这一关是否可解。
- **view 管几何**:世界坐标、缩放、缓动、材质。

但**几何约束本身住在 core**。例如轨道的形状、周长、每格弧长、一组乘客的排布(`track-shapes.ts` / `track-path.ts`)都在 core 里,因为 `validateTrack` 必须在关卡数据落盘之前就能判断"这个环长这个形状画不画得下"。view 从 core 读这些常量,不自己另存一份。

## 跑起来

### 玩

用 Cocos Creator 3.8.7 打开 `game/` 目录,打开 `assets/main.scene`,点预览。

### 两道闸门

改完代码必须都过:

```bash
cd logic
npm install              # 首次
npm test                 # core 的单元测试(jest)
npm run typecheck:view   # 表现层的类型检查(tsc,不跑测试)
```

`view/` 没有测试环境 —— 它 import 'cc',jest 加载不了。所以它的闸门只有类型检查,逻辑正确性靠把可测的部分推回 core。

### 看 core 到底怎么想的(调试叠加层)

预览里按 **D** 键,给每辆车画出 core 真正在推理的那个矩形:**绿色 = core 认为能开出去,粉色 = core 认为被挡**。

车没有端正地待在自己的框里,就说明它被画到了 core 没在看的地方 —— 那是表现层的 bug,core 的判定看起来会跟着一起错。同档位的车框永远一模一样;要是框对齐了而车身不一样大,那是车身错了,不是 `CAP_BOX` 错了。框画在车的**上方**(z = 1.2),正交相机下这不产生任何横向位移 —— 所以**框要是从车上滑开了,本身就证明投影不是正交的**。

### 重新生成关卡

关卡不是手写的,是离线算出来的:

```bash
cd logic
npm run gen
```

它把 `tools/gen-levels.ts` 和 core 一起编译到 `.tmp/gen`,用普通 node 跑一遍,写出 `game/assets/resources/levels/level-N.json`,并打印一张表(每关的车数、颜色数、初始被挡车数、难度分、乘客总数)。

**改了 core 里任何影响关卡数据的东西(环长、容量、难度曲线),都要重跑一次 `npm run gen` 并把 JSON 一起提交**,否则运行时的关卡和代码里的规则会对不上。

### 关卡编辑器

```bash
cd editor
npm install
npm start          # 起一个本地静态服务
```

## 生成关卡的思路

关卡是**构造出来就一定可解**的,不是随机撒完再验证:

1. **pack**:先只摆形状,不定方向,把车填进网格。
2. **peel**:反复挑一辆"存在一个合法方向、且那个方向上有一条通路能开出去"的车,拿掉它。**剥离的顺序本身就是一份通关解法**。

早先的版本是随机撒 + 拒绝采样,密度到 75% 就再也撒不出可解局面了;换成 pack-then-peel 之后,36 辆车、超过 80% 的网格占用率都稳定可解。

难度曲线在 `level-gen.ts` 的 `TRACK_CURVE` 里,现在只剩两个旋钮:**每条候补通道显示几批乘客**,以及**有两条通道还是一条**。环长不再是旋钮 —— 由形状的周长唯一决定(见下)。

## 几个容易踩的不变量

这些都在代码注释里写着原因,这里只列出来提醒:

- **环长由形状决定**。每种轨道形状的合法环长由 `capacityOptions()` 算出,依据是"组与组之间的裸地(seam)"要落在 `SEAM_MIN..SEAM_MAX` 之间 —— 太小看不出行,太大看着空。目前四种四边形是 28 格,圆形 24 格。
- **环长必须是 4 的倍数**,因为两条通道的入口在 `boardIndex ± capacity/4`,除不尽就会落到拐角上,而入口的法线必须接近水平。
- **`GROUP_SIZE` 必须能整除所有车容量(16 / 24 / 32)**。现在是 4(一横排 4 个人)。取 12 就不行 —— 会把一种颜色的乘客切成"若干满组 + 一个残组",轨道上出现半空的格子。
- **能把环压多紧,是拐角说了算**(上车口曾经是,现在不是了)。格子一短,拐角内侧的一排就会贴上前一排 —— `minRowGap` 量的就是这个,下限 `BLOCK.clearance` 等于人宽:不同组的人可以挨上,不能重叠。32 格时有三种形状过不了,所以 `CAPACITY_OPTIONS` 停在 28。
- **`minRowGap` 只比较相邻两格之间的距离**。它曾经把"同格内"的对也算进去 —— 而一排是刚体,同格内的距离恒等于 `acrossStep`,永远是最小值,于是拐角的测量被一个常量遮住了,`capacityOptions` 检查的是同义反复。改这个函数时别把同格的对加回去。
- **椭圆是最紧的那条曲线**。其他形状的拐角由 `RECT_R`/`HEX_R`/`TRAP_R` 决定,椭圆没有圆角参数,最紧曲率就是 `halfH²/halfW` —— 所以缩窄 `halfW` 时 `halfH` 不能跟着一起缩,否则椭圆先崩。
- **一排乘客本身比人略窄**(`acrossStep` 0.20 < 人宽 0.22,头部重叠约一成)。这不是失手 —— 决定"看不看得出行"的是**跨组最近距离与组内最近距离的比值**,所以把一排收窄能换来更小的组间缝。想改宽回去,缝就得同步放大。
- **停车场没有格子**。车是**连续坐标 + 朝向角**(`CarSpec` 的 `x`/`y`/`angle`,度,0° = +X 逆时针),碰撞体是有向矩形,判定在 `core/geometry.ts`。板坐标原点在场地中心、**+Y 朝上**,1 板单位 = 老网格的格距 0.7533 世界单位 —— 相机取景和地板因此在自由角度改造中一行没动。
- **相机必须是正交的,这不是审美问题**。玩法是纯 2D,core 判定的是车在板面上的 footprint;但车是**立在**板面上画的,车顶离相机近 `hgt`(见 `buildCar`)。透视相机会把车顶按 `d/(d−hgt)` 放大并沿径向往外推 —— 而停车场中心在 y = −2.73、相机轴在 y = 0,整场偏轴,场地底部离轴约 5 个单位。实测十关:车顶落点离 core 所算的 footprint **中位数差 0.109 板单位、最大 0.187**,而 `CLEARANCE` 只有 0.04。画面撒的谎是整个间距预算的 2~5 倍,一次坏三样:**挡路判定**(用 core 自己的扫掠跑投影后的盒子,360 辆里 13 辆与 core 不一致,其中 10 辆是「core 说能走、眼睛看是被挡」)、**尺寸档次**(看到的是车顶加透视露出的侧壁,越偏轴露得越多 —— 两辆同为 `medium`、同模型同 `CAP_BOX` 行的车,宽度能差 26%,73 辆 medium 里 34 辆画得比某些 big 还宽)、以及**点击拾取**(`onTap` 把射线打在板面、`pickCar` 测的是 footprint,而玩家瞄的是没盖在盒子上的车顶)。正交之后,车无论多高、停在哪里都精确投影到自己的 footprint —— 在场内、在环道上、停进车位时都成立。`orthoHeight` 取的就是原来 45° 垂直 fov **在板面上**的半高,所以 z = 0 的取景一像素没动,别的东西至多挪回它原本被放大的那 2.4%。**要把透视放回去,就得先让 core 也认识车顶那个平面。**
- **补间动画的回弹目标必须是「静止姿态」,不能是「当前值」**。`squash` 原本用 `body.scale.clone()` 当回弹终点 —— 而一次被拒绝的点击会对同一个 body 压两次(`onTap` 一次,`playShake` 撞上障碍时再一次),第二次落在第一次里面的概率是 **99.2%**(nudge 段下限 0.12s,而这个补间要 0.18s,被挡的车 gap 中位数只有 0.01 板单位)。于是第二次把**动画中途**的缩放当成了静止姿态,而且**逐次累积**:拒绝一次 (0.987, 1.018),十次长宽比偏 36%,二十次偏 85%。被挡的车恰恰是玩家反复点的车 —— 这就是「同一种车尺寸不一样」的来源,也让车身画得比 core 认为的宽出近两成、看着像压进了旁边的车道。现在 `squash` 用 WeakMap 记住首次的静止缩放,并在开始前按 tag 停掉仍在跑的那一个。**同一个节点上叠补间,就得先停旧的、并回到已知姿态。**
- **`CLEARANCE`(0.04 板单位)在四处使用,而且每一处都必须「一对各分一半」**:`validateLevel` 的两两校验、`packBox`、`firstBlocker` 的车道扫掠、`pickCar` 的点击放宽。两边用同一个值,规则才读得懂 —— **看着过不去的缝,就是真的过不去**。它取的是格子时代**最紧**的那个间隙(小车头尾 `1 − 0.964 = 0.036`),不是平均值。

  **「一半一半」不是写法问题,是正确性问题。** 把整个间距堆在一辆车上、另一辆不膨胀,在可以旋转的矩形上是**另一条规则**:矩形膨胀 `d` 后在轴 `n` 上的投影半径增加 `d·(|n·u| + |n·v|)` —— 正对时是 `d`,45° 时是 `d√2`。所以整份堆在一辆上最多能到 `√2·CLEARANCE`,而两边各半最少只有 `CLEARANCE`。**格子时代所有车轴对齐,两者恒等,谁也没发现;自由角度一来立刻分家。** 后果是 `validateLevel` 判合法的一对,在 `firstBlocker` 里却重叠 —— 而 `sweepHit` 对已重叠的盒子**无论朝哪个方向都返回 0**,于是车被判「被身后的车挡住」。十关 360 辆里有 15 辆中招,15 辆全部是 gap 恰好为 0、挡路车偏离车头 128°~159°。**再加一个读 `CLEARANCE` 的地方,就分一半。**
- **`firstBlocker` 只在满足 `CLEARANCE` 的场地上才有意义**。膨胀后的车一旦与邻车重叠,`sweepHit` 无论朝哪个方向都返回 0 —— 于是排得过密的一整列车全部报"被挡",连最前面那辆也是,而且报出来的 blocker 可能在**后面**。是 `validateLevel` 的三条几何规则让它成立的。
- **`CAP_BOX`(`core/types.ts`)是车身尺寸的唯一事实**,view 反过来按它缩放模型。这是主从倒置 —— 以前是模型 AABB 去适配格子、尺寸算出来。**别再从模型反推 `CAP_BOX`**,会绕成一个圈。
- **换车辆模型之后先跑 `node tools/check-car-models.mjs`**。模型的**绝对尺寸无所谓**(每档车各自算一个 `s`,画出来必然是 `CAP_BOX × 格距`),有所谓的是**长宽比**:`s` 取两轴的 `min`,比例一漂,一个轴顶住、另一个轴就填不满 —— 车填不满 packer 给它留的位置,缝就出现在那里。core 读不了 `.glb`,所以这个脚本是唯一能发现 `CAP_BOX` 与模型脱节的东西,而失效方式是**静默且不对称的**:模型变大反而让车和点击判定一起**变小**。零依赖,超差以非零码退出,并直接给出该填的数值。
- **`pack` 用分离松弛,不是拒绝采样**,而且它**不保证收敛** —— 收不敛就返回空数组让 `generateLevel` 换下一次尝试。信不信它的输出,由 `validateLevel` 的三条几何规则说了算。
- **`packBox` 比 `validateLevel` 多留 `ROUND_MARGIN`(1.5e-4)**。松弛的不动点是"两两几乎相切",而 `scatter` 之后把坐标舍到四位小数,能让相切的一对再靠近约 1.4e-4 —— 少了这点余量,86% 的满员尝试会被自己的校验丢掉,难度搜索的有效样本从 200 次掉到 2~5 次。
- **剥离时每辆车只有 `angle` 和 `angle + 180` 两个朝向可选**。矩形在半周旋转下与自身重合,所以摆位定了、朝向还能二选一 —— 这也是 `peel` 与 `isSolvable` 的占用模型完全一致的原因。
- **场地的面积占用率约 45%(逐关 41.7%~50.0%),不是格子时代注释里的 88%**。后者数的是"占了多少格",差额正是方格里塞长条车时四周那圈空气。逐关波动是因为每辆车的档位是独立抽样,36 次抽样的车型组合本身就有几个百分点的方差。
- **难度曲线的 blocked 区间是量出来的,不是定出来的**(`BLOCKED_FIRST`/`BLOCKED_LAST`)。斜向通道是斜的扫掠带,蹭到的车比正交多,分布整体上移。**但这个测量有两层循环要绕开**:一是读十个已发布关卡的 `blocked`,报的只是"搜索在旧目标下找到了什么";二是就算换到目标不动的那段(id 11 以后曲线是平的),生成器**只接受落在旧容差窗口内的候选**,所以观测到的上下端(24 和 30)是**窗口的边,不是几何的边**。窗口内部的形状是可信的(取第一个命中,窗口内无偏),下限 21 也是可信的(它来自 id 1~10,那几关的旧窗口一直探到 15、没被截断)。上限则不知道。
- **`routeToSlot` 的第一段开到环道,不是开到停车场边缘**。停在边缘意味着车**中心**刚跨过边界、车身还有一半在场内,下一段原地转向就会把车尾扫过旁边还停着的车 —— 实测 360 辆里有 221 辆穿模。开到环道则是 0 辆,而且大多数车的第二段变成零长度被 `driveRoute` 丢掉,回到改造前那种一段式出场。
- **一辆车停进车位时只会变小,不会变大**(`stallScale` 对 1 取 `min`)。车位比车长,不加这个上限的话小车停进去会凭空放大。
- **`pickCar` 在车自己的坐标系里做盒判定**,并额外放宽半个 `CLEARANCE`。轴对齐的盒子对斜停的车能宽出四成,点旁边的空角会点中它;而放宽半个间隙是**可证明安全**的上限 —— core 保证任意两车身间隔一整个 `CLEARANCE`,所以两个放宽后的盒子仍不可能同时包含一个点,"第一个命中"依然无歧义。要更大的点击面积,就得改成"取最近的车"而不是"取第一个包含的车"。
