> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the lobby read as a drawn scene rather than a diagram: sharp edges, three ground layers, badges with thickness, and the bar's controls moved to a column down the left.

### Three findings that change what "done" means

These were established before the plan was written. An implementer that ignores them will do work that changes nothing on screen.

**(A) Requirement 1's premise is wrong, and its real cause is elsewhere.** A badge draws exactly three things (`home-view.ts`'s `buildStop`): a glow, a base disc, a face disc. **There is no shadow on any badge or button to re-parameterise.** The road's shadow already *is* `offset(2, -3)` at `SHADOW_INK` alpha 64, and 64/255 = 0.25. What the player photographed as 大面积柔光 around the badges is **texture magnification**: `ui-shapes.ts`'s `DOT_SIZE = 32` gives every circle in the project one 32x32 frame, and a badge drawn at 170 design units is about 155 device pixels on a 1170-wide phone — a 4.8x blow-up of an antialiased edge. That is also the 模糊 in "1 2 这些关卡按钮有些模糊". **Task 1 fixes it at the texture; nothing about shadow constants changes.**

**(B) The grass is a new colour, chosen deliberately over the shared table.** Round 1's P0 required the lobby to read from the board's own palette. A grass green is not in it. The user was asked and chose **(b): the lobby gets its own ground colour, and `palette.ts` marks it lobby-only.** So `palette.ts` grows a clearly-labelled lobby section; the board's entries are untouched.

**(C) There are no car "thickness/outline/light constants" to share.** Cars are `MeshRenderer` meshes lit by a scene light (`car-builder.ts` uses `shadowThrow(LIFT.contact)` and `car-mesh.ts` builds geometry). The lobby is a flat orthographic UI canvas with no lights and no meshes. Requirement 5 is honoured in **appearance** — a darker side showing below the top face, plus a dark outline — and the docblock must say that it is deliberately a resemblance and not a shared constant, so nobody goes looking for a `car-builder` import that cannot exist.

## Global Constraints

- **Language.** Code, comments, identifiers, commit messages and file names are **English**. Only user-facing UI strings are Chinese. Code blocks in this plan are **intent drafts, not text to transcribe**.
- **Layer discipline.** `core/` is pure TypeScript and must never `import 'cc'`. `view/` imports `cc` and has no test environment.
- **Canvas.** 1280 design units wide, always (`FIXED_WIDTH`). Height varies — about 2770 on a 19.5:9 phone, 1707 on a 4:3 tablet. X may be an absolute design unit; **Y must derive from `canvasSize(canvas).h`**.
- **No image assets.** Every shape is painted at runtime by `ui-shapes.ts` into a small RGBA texture, white so it can be tinted, and the frames are cached.
- **`.ts.meta` files are repo-tracked.** Every new `.ts` under `game/assets/` carries one. `git add` both, same commit.
- **Out of scope:** the badge's circular outline shape, the Bézier path's winding, `legSamples`/`nodeCenter`'s curve, and the in-game board and HUD.
- **Test gate.** `cd logic && npx jest --testPathIgnorePatterns=level-gen --forceExit` (the `level-gen` suite is a known pre-existing slow one that leaks timers — excluding it is expected, and say so in the report) and `cd logic && npm run typecheck:view` (the `package.json` is in `logic/`, not the repo root). `typecheck:view` sets `strict` but **not** `noUnusedLocals`, so it catches no orphaned import or constant — check those by reading and by grep.

### Task 1: sharp circles

**Requirement 1, and the 模糊 complaint. Finding (A) is the brief.**

**Files:** `game/assets/scripts/view/ui-shapes.ts`, `logic/tests/view-source.test.ts`

`DOT_SIZE = 32` and a single module-level `dotFrame` serve every circle in the project — a 22-unit unread dot and a 200-unit glow alike.

**What to build:** frames cached **per size bucket**, exactly as `roundedSprite` already caches per corner radius. `dotSprite(name, d, color)` picks the bucket from `d`: the smallest power of two that is at least `d`, clamped to 32..256. A 170 badge takes 256, a 52 coin takes 64, a 22 dot takes 32.

- Keep the cheap case cheap: the dot on the bar must not start paying for a 256-square texture.
- The clamp's top end matters: 256x256 RGBA is 256 KB, and the largest circle the lobby draws is about 200 design units. Unbounded bucketing would let a future caller ask for a 4 MB texture by passing a big number.
- `STAR_SIZE`'s docblock already reasons about exactly this for the star ("a 32px frame -- the size the dot gets away with, being a circle at 40 -- would be visibly soft at that magnification"). **The dot stopped getting away with it when the badge became a 170-unit circle.** Say so; that docblock's claim is now the counter-example.

- [ ] **Step 1:** Replace `dotFrame` with a `Map<number, SpriteFrame>` and a bucket function. Rewrite `DOT_SIZE`'s docblock.
- [ ] **Step 2:** `npm run typecheck:view`.
- [ ] **Step 3:** Add a source guard: `ui-shapes.ts` has no single module-level `dotFrame`, and the bucket is clamped at both ends. Make it able to fail.
- [ ] **Step 4:** Run the suite. Commit.

3. **Road** — `ROAD_W` at `ROAD`, unchanged.

**The centre dashes (requirement 4)** come from the board's, which are real and worth matching rather than inventing: `scene-stage.ts:199` uses `dash = 0.18, gap = 0.13, thick = 0.05` in board units with `LOT_DASH` (206,212,224). Walk the same `legSamples` polyline and place dashes along it by arc length, skipping the gaps; a dash is a `roundedSprite` at `radius = thickness / 2`, which is the capsule identity `strokePath`'s docblock already sets out.

### Task 6: seven or eight of the smaller badges

**Requirement 6's pitch half. Task 5 must be merged first.**

**Files:** `game/assets/scripts/core/home-path.ts`, `game/assets/scripts/view/home-view.ts`, `logic/tests/home-path.test.ts`

**Re-derive `RAIL_PITCH` from scratch against Task 5's badge.** Do not scale the old number. The docblock's own heading is the instruction, and it has now been wrong five times across three rounds:

- **CHECK WHICH ADJACENCIES ARE REACHABLE BEFORE SIZING AGAINST THEM.** `levelState` is monotonic, so the only adjacent pairs that exist are (done, done), (done, current), (current, locked), (locked, locked). A `done` badge directly above a `current` one cannot occur. Read `core/level-state.ts` and confirm it yourself.
- **A badge is not symmetric about its centre.** It reaches `r * scale` UP and `(r + side) * scale` DOWN, where `side` is Task 5's thickness. The current badge also wears the 2-unit outline, which is concentric — the same reach in every direction.
- The star row hangs below a `done` badge only. `starsFor` returns 0 for `current` and `locked`; check it.
- Say, once, that the table is a **vertical projection** and therefore a conservative bound: adjacent stops are `2 * ZIG_X` apart across the screen as well, so the true closest approach is much larger. The previous round's docblock gained that sentence; keep it.

Then check the band actually holds 7-8: `barBottom` to the start button's top, divided by the new pitch, on `h` = 2770. Report the figure.
