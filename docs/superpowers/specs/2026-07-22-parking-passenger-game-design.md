# 挪车接客小游戏 — 设计文档

- 日期:2026-07-22
- 平台:微信小游戏
- 引擎:Cocos Creator
- 后端:无(纯单机,本地存档)
- 状态:设计已确认,待编写实现计划

## 1. 产品定位

一款单机休闲解谜游戏。玩法为**双层复合**:

- **底部**:挪车解锁谜题(类 Parking Jam)。停满带箭头的车,点车沿箭头方向直线开出,被挡则开不出。
- **顶部**:传送带式循环接客。彩色乘客在循环轨道上绕圈走动,走到"上车位"时若停车位有同色车则上车;车坐满自动开走。

**上线目标 = 纯单机闯关**,不含排行榜/内购/云存档/广告。这些为未来可选扩展(届时可接微信云开发),当前不做,不预留过度设计。

## 2. 核心玩法规则

### 顶部(乘客 + 停车位)
- 顶部有一条**循环轨道**,彩色乘客在上面不停绕圈走动。
- 中间有 **7 个停车位**:初始 **4 个可用、3 个锁着**。
- 乘客**只能上同色的车**。
- 车容量按尺寸:**大车 32 人 / 中车 24 人 / 小车 16 人**。
- 乘客走到轨道上的**上车位**时,若某停车位停着**同色且未满**的车,则上车,乘客的循环位空出。
- 空出的循环位绕回**排队通道**时,从乘客池补齐下一个乘客。
- 停车位里的车**坐满后自动开走**,腾出车位。

### 底部(挪车网格)
- 网格停满带箭头的车,每辆车有朝向(上/下/左/右)、尺寸、颜色。支持多格车(如横向大巴)。
- 点车 → 沿箭头方向逐格检测;通路则驶出网格并停入一个空停车位;被挡则不动(抖动反馈)。
- **停车位满了 → 底部的车开不出来**(需先有车坐满开走腾位)。

### 胜负
- **过关**:乘客池空 + 循环上无乘客 + 所有车位空 + 网格无车。
- **卡死(失败)**:车位全满,且无一辆车能坐满(没有对应色乘客可上),且网格无车能开出 → 死局。检测到弹出"失败/用道具/重来"。

### 道具
- **刷新**:重排网格车朝向。
- **硬消**:直接开走一辆网格车,忽略阻挡。
- **磁铁**:把指定车吸出到车位。
- 均通过逻辑层统一接口修改状态。

## 3. 架构:逻辑与表现分离

核心逻辑为纯 TypeScript,不依赖 Cocos 节点,可脱离画面单元测试。

```
逻辑层(纯 TS,可单测)
├── LevelData        关卡数据模型(网格、乘客队列、车位配置)
├── GridSystem       底部网格:车的位置/朝向/尺寸/颜色,占位管理
├── MoveSolver       挪车判定:某车沿箭头方向能否开出(碰撞检测)
├── ParkingSystem    停车位:分配空位、锁定位管理、满员判定
├── LoopSystem       顶部循环:乘客队列、上车位、补位、乘客池
├── BoardingSystem   上车结算:同色匹配、容量、坐满开走
└── GameCore         状态机:进行中 / 过关 / 卡死,协调各系统并派发事件

表现层(Cocos 节点/组件)
├── GridView         网格与车渲染、点击输入
├── LoopView         循环轨道 + 乘客动画
├── ParkingView      车位与停靠车动画
├── HUD              关卡号、进度、金币、道具按钮
└── SceneFlow        主菜单 → 关卡 → 结算 界面流转

工具
└── LevelEditor      关卡编辑器(独立场景,导出 JSON)
```

**原则**:所有"合法性/胜负"判断都在逻辑层;表现层只负责渲染和收输入。所有状态变更(上车、开走、补位、挪车)通过 `GameCore` 派发事件,表现层监听事件播动画。逻辑可用"逻辑步进"方式单测,不需跑游戏。

## 4. 关卡数据格式(JSON)

编辑器导出、运行时加载的契约:

```jsonc
{
  "id": 4,
  "grid": {
    "cols": 7, "rows": 8,
    "cars": [
      // 每辆车:左上角坐标、尺寸、朝向、颜色、容量
      { "x": 0, "y": 0, "w": 1, "h": 2, "dir": "up",   "color": "red",  "cap": "small" },
      { "x": 2, "y": 1, "w": 2, "h": 1, "dir": "left",  "color": "blue", "cap": "big" }
      // cap: small=16 / medium=24 / big=32
    ]
  },
  "parking": {
    "slots": 7,
    "unlocked": 4          // 其余 3 个锁着
  },
  "loop": {
    "capacity": 20,        // 循环轨道上同时可见的乘客位数
    "boardIndex": 5,       // 上车位在循环轨道上的索引
    "queue": [             // 乘客池,按顺序依次补位到循环
      { "color": "red",  "count": 16 },
      { "color": "blue", "count": 32 },
      { "color": "red",  "count": 8 }
    ]
  },
  "powerups": { "refresh": 3, "hardClear": 1, "magnet": 1 }
}
```

### 设计约束(保证可解 + 好配关)
- **守恒校验**:每种颜色乘客总数 = 该颜色所有车容量之和。编辑器导出时自动校验,不平衡报错。这是"有解"的必要条件。
- **颜色**:固定枚举(red/blue/green/yellow/purple/cyan…),车与乘客共用。
- **尺寸→容量**映射集中配置,不写死在关卡里。
- 多格车 `w/h` 的占位登记在 GridSystem。

## 5. 核心循环

### 底部(离散/事件驱动,玩家点车触发)
1. 点车 → `MoveSolver` 沿箭头逐格检测。
2. 被挡 → 抖动反馈,不动。
3. 通路 → `ParkingSystem` 找空位;有则驶出停入,无则提示"车位已满"。
4. 网格移除该车,释放占位。

### 顶部(实时/帧驱动,持续运行)
1. `LoopSystem` 每帧推进乘客绕圈(匀速,速度可配)。
2. 乘客到上车位 → 检查车位有无同色未满车:有则上车、循环位空出;无则继续绕。
3. 空循环位绕回排队通道 → 从乘客池补齐。
4. 车坐满 → 开走,释放车位,触发死局检测。

## 6. 里程碑

- **M1 — 核心逻辑层(纯 TS)**:GridSystem/MoveSolver/ParkingSystem/LoopSystem/BoardingSystem/GameCore。TDD:先写规则测试,再实现。产出可用代码跑通整关的内核 + 测试全绿。
- **M2 — 表现层(能玩一关)**:GridView 点击挪车、LoopView 乘客循环、ParkingView 停靠、HUD。手搓 2~3 关验证手感。
- **M3 — 关卡编辑器**:独立场景摆车/配队列/设车位道具,守恒校验,导出 JSON。产出首批 20~30 关新手曲线。
- **M4 — 系统与上线**:关卡选择、本地存档(`wx.setStorageSync`)、道具、结算页、音效震动、微信发布配置、类目资质、隐私合规、性能优化(合图/对象池)。

## 7. 测试策略

- **逻辑层**:单元测试(独立 tsconfig + Jest,或 Cocos 内跑 TS 测试)。核心规则必须有测试。
- **可解性**:编辑器导出跑守恒校验;关键关卡写"回放测试"(给定操作序列 → 断言过关)。
- **表现层**:手动测 + 少量集成测试。
