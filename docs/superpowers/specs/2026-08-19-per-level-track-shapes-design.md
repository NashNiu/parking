# 每关不同的轨道形状与通道配置设计文档 (M7)

> 状态:四个决策已确认(形状库/数据驱动/通道跟随/前瞻语义),待用户书面审阅。
> 日期:2026-08-19
> 前置:M6(双通道候车轨道)已完成并合入 master。

## 目标

让**转盘的形状**和**候车通道的配置**每关不同,并且这些差异是**真的难度旋钮**,不是装饰:

- 转盘长度(环上格数)= 缓冲有多大、同时能看到几种颜色;
- 通道长度(画出的候车批数)= 玩家能提前看到几批颜色;
- 单侧还是双侧通道、单侧在近端还是远端 = 新乘客从进场到抵达上车口要几拍。

## 用户原话拆解

1. 乘客的转盘和通道的形状每关都不同。
2. 不用太复杂的样式:四边形、六边形、梯形、圆形、椭圆形。
3. 主要通过转盘的长度来控制难度。
4. 不一定每关都需要两侧有通道,也可以只有一侧有通道。
5. 通道和转盘的长度都是用来控制关卡难度的。

## 已确认的四个决策

- **形状库,每关换一种**:五个手调好的轮廓,不是自由参数化。
- **形状写进关卡 JSON**:`loop.track` / `loop.feeds` 两个可选字段,由离线生成器按关号写入;缺字段的关卡回退到现状。
- **通道跟着轨道走**:通道位置与朝向从**入口格自己的路径点 + 外法线**推出,通道自身不进形状库。
- **"通道长度"= 前瞻长度**:画出来的候车批数。乘客总队列仍然比通道长,多出来的隐含在通道外。载客量(`CAP_SIZE` 16/24/32)与难度曲线的车数/颜色数部分**不动**。

## 硬约束:几何预算

轨道能占的空间已经在 M5/M6 定死了,这一版**不动相机、不动 HUD、不动停车场**,所以所有形状共用同一个外框:

| 方向 | 界限 | 由什么定 |
|---|---|---|
| 半宽 2.6 | 通道最外缘 ≤ 4.67 | 轨道深度处的可视半宽(见 `buildLanes` 注释) |
| 半高 1.3 | 带底 2.12、投影底 2.05 | 停车位面板顶边 2.05(`PARKING_Y` 1.4 + 面板半高 0.65) |

纵向余量是 **0**,横向是 **0.02**。所以形状变的是**外框内的轮廓**,不是外框本身。想要更大的转盘,得先把相机 fov 轴换成横向、或者把 HUD 标题挪走 —— 那是另一个里程碑。

横向预算还进一步限制了前瞻长度:

```
通道最外缘 = 入口点 x + BAND_HALF(0.38) + LANE_START(0.52) + (前瞻 - 1) × LANE_STEP(0.45) + 0.25 ≤ 4.67
```

固定开销吃掉 3.75(四边形),只剩 0.92 —— 按 0.45 的候车间距**只够 3 批**。前瞻上限因此是**几何算出来的**,每个形状不同,不是拍脑袋定的常量。

## 五个形状

全部左右对称,缺口在 t=0.5(底部正中,对着停车场),按**顺时针**从顶部中点起步。实测值:

| 形状 | 定义 | 周长 | 入口点 (t=0.25) | 入口外法线 \|ny\| | 最小曲率 | 前瞻上限 | 可用格数(行距) |
|---|---|---|---|---|---|---|---|
| `rect` 四边形 | 顶点 (±2.6, ±1.3),圆角 0.60 | 14.57 | (2.60, 0.00) | 0.000 | 0.60 | 3 | 8(1.82) 12(1.21) 16(0.91) 20(0.73) |
| `hex` 六边形 | 顶点 (±1.7, ±1.3) + (±2.6, 0),圆角 0.60 | 12.72 | (2.47, 0.00) | 0.000 | 0.60 | 3 | 8(1.59) 12(1.06) 16(0.79) |
| `trap` 梯形 | 顶点 (±1.9, 1.3) + (±2.6, −1.3),圆角 0.60 | 13.18 | (2.30, −0.18) | 0.260 | 0.60 | 3 | 8(1.65) 12(1.10) 16(0.82) |
| `oval` 椭圆 | 半轴 2.6 × 1.3,120 段折线 | 12.59 | (2.60, 0.00) | 0.000 | 0.65 | 3 | 8(1.57) 12(1.05) 16(0.79) |
| `circle` 圆形 | 半径 1.3 | 8.17 | (1.30, 0.00) | 0.000 | 1.30 | 5 | 8(1.02) |

圆角**三个形状都是 0.60**,不是各挑一个好看的值:0.60 是满足下面那条曲率下界的最小值。第一版写的 0.40 / 0.35 / 0.30 全都低于 0.6,而同一份文档的校验规则 7 又要求 ≥ 0.6 —— 那是自相矛盾,实现期由测试当场暴露。0.6 之下的选择要么让一行 4 人在拐角处折叠,要么让规则变成空话。

几点必须写进代码的:

- **圆形是天生的短转盘**。它要塞进纵向 1.3 的死限,半径只能 1.3,周长只有四边形的一半 —— 只支持 8 格一种配置。这个咬合是几何给的,正好和难度方向一致:越往后转盘越小越圆。
- **椭圆用折线,不用参数方程**。参数方程的 `at(u)` 不是等弧长的,行会在两端挤在一起;120 段折线的等弧长行走是精确的,与真椭圆的偏差 < 0.001。最小曲率取解析值 `b²/a = 0.65`。
- **圆形可以用一个整圆弧段**。圆的参数化本身就是等弧长的。
- **每个 builder 自己从顶部中点起步**,顶边劈成两段(现有 `buildSegments` 就是这么做的),或者参数从 90° 起。**不要事后数值搜索起点** —— 那样左右对称只能做到搜索精度(1e-3),而分析起步是精确的(1e-9),测试才立得住。
- **梯形的入口不在最宽处**。它上下不对称,最宽的是底部两角;t=0.25 落在斜边上 (2.30, −0.18),外法线下倾 15°,所以通道会略微斜向下。通道底边落在 y = 3.8 − 0.18 − 0.38 = 3.24,离停车位面板顶 2.05 还有 1.19,安全。

### 格数必须是 4 的倍数

入口格是 `board ± capacity/4`。格数不是 4 的倍数时这个除法要取整,入口就**落不到四分点上** —— 六边形 18 格的近端入口落在 t=0.222,那里已经是斜边,外法线倾了 30°(\|ny\| = 0.569),通道会斜着插出去;椭圆 14 格同样(0.578)。这两个组合是校验规则 6 抓出来的,不是预览发现的。

所以 `capacity ∈ {8, 12, 16, 20}`,`q = capacity / 4` 精确整除,入口精确落在 t=0.25 / 0.75。代价是格数粒度变粗,**圆形只剩 8 格一种配置**(12 格行距 0.68 低于下界)—— 它本来就是最紧的那个环,一种配置够了。

备选方案都更差:把通道钉在几何四分点而让行从最近的格进场,会留下 0.4 单位的错位(行走进来之后停在门口旁边);给索引→t 的映射加半格相位,则是把错位转移到**上车缺口**上,而缺口对着停车场、起飞几何依赖它 —— 更不能动。

### 行距的上下界

`行距 = 周长 / 格数`,合法区间 **[0.70, 1.90]**:

- 下界:一行沿路径方向只占一个人偶的宽度(约 0.25),但上车缺口是绝对弧长 0.55 —— 行距 0.70 时缺口两侧各只剩 0.075 的白带,再密下去缺口就和相邻行糊在一起,"洞转过来了"读不出来。
- 上界:超过 1.90 环上过于空旷,一圈只剩几行,轨道读起来像空的。

### 缺口宽度改成绝对值

现在缺口是**半格**(`half = 0.5 / capacity`),会随格数缩小 —— 20 格时只有 0.37,门口小到读不出来。改成**绝对弧长 0.55**,每关的门口一样大。0.55 < 行距下界 0.70,所以缺口永远不会吞掉相邻行。

## 难度模型

三个旋钮统一成一个可排序的量:

```
规划视野(拍) = 前瞻批数 + 管道拍数
管道拍数:近端 = capacity / 4,远端 = capacity × 3 / 4
```

**两侧通道并不等价。** 环每拍朝一个方向转 1 格,近端入口的行走 1/4 圈到上车口,远端要走 3/4 圈。核心现在是**远端先排空**(即今天的 `left`),所以双通道关卡自带一次压力升级:开局视野宽,远端空了之后掉到近端的值。单通道关卡则是全程恒定一个压力值。

这个升级是 M6 `left drains first` 行为的副产品,不用新写代码,但要在数据里用 `far` / `near` 而不是 `left` / `right` 把它说出来(见下)。

## 数据格式

`LevelData.loop` 的增量,两个字段都可选:

```ts
loop: {
  capacity: number;          // 8 | 12 | 16 | 20,上限由形状周长决定(圆形只支持 8)
  boardIndex: number;        // 必须 == capacity / 2(缺口在底部正中)
  track?: TrackShape;        // 缺省 'rect'
  feeds?: Feed[];            // 缺省 [{ side: 'far', lookahead: 3 }, { side: 'near', lookahead: 3 }]
  queue: QueueGroup[];
}

export type TrackShape = 'rect' | 'hex' | 'trap' | 'oval' | 'circle';

/** 一条候车通道。`lookahead` 是画出来的批数,也就是玩家的前瞻长度。 */
export interface Feed { side: 'far' | 'near'; lookahead: number }
```

**为什么用 `far` / `near` 而不是 `left` / `right`**:两侧的管道长度差 2 倍(1/4 圈 vs 3/4 圈),`left` 这个名字把这件事藏起来了,而它恰恰是这一版的难度旋钮。屏幕左右的映射只在视图里出现一次(`far` → −x,`near` → +x,因为环是顺时针转的)。代价是 `LoopSystem` 的 `left` / `right` / `entryLeft` / `entryRight` 要改名。

**缺省值就是今天的行为**,所以不带新字段的关卡(以及关卡编辑器产出的旧文件)照旧能跑。注意默认 `rect` 的圆角从今天的 0.8 收到 **0.60** —— 让"四边形"和"椭圆"在画面上分得开是这一版的重点,而 0.60 是曲率下界允许的最小值(再小就会让一行 4 人在拐角处折叠)。如果你更喜欢今天那个软角,评审时说一声即可。

### 入口格与管道

入口**在索引空间里定义**,不需要形状声明什么"dock":

```
board     = capacity / 2
q         = capacity / 4             // 精确整除,见「格数必须是 4 的倍数」
entryNear = board - q                // 管道 q 拍
entryFar  = (board + q) % capacity   // 管道 capacity - q 拍
```

通道和缺口都画在 `t = entry / capacity` 上 —— 不是画在形状的"最宽处"。这两者只在双对称的形状上重合;梯形的 t=0.25 落在斜边上,通道就顺着那里的外法线斜着接出去,照样贴得住。形状要满足的只有一条:**该点的外法线接近水平**(见校验规则 6),否则通道会插进 HUD 或停车场。

### LoopSystem 泛化

`left` / `right` 两个固定字段变成 `feeds: { side, queue, entry }[]`,1 或 2 条:

- 排空顺序仍然是**远端先、近端后**;单通道时就那一条。
- 装填时把剩余批次按顺序分给各通道(双通道 = 今天的对半分;单通道 = 全给它)。
- `reachableColors()` 按**排空顺序**遍历 feeds —— 死局判定完全靠它,单通道下必须与今天的语义一致。这是这一版风险最高的一处改动。

## 校验规则(新函数 `validateTrack`)

规则住在一个**新函数**里,不是加进 `validateLevel` —— 写实现计划时读代码才发现:`validateLevel` 是 `isSolvable` 的判据(`solvability.ts:35`,失败即判不可解),而 `logic/tests` 里的合成关卡故意用 capacity **2 / 4 / 5 / 6**(`game-core` 的死局用例靠 capacity 2 让两个入口重合在 index 0),这些夹具**从不需要被画出来**。把可绘制性塞进 `validateLevel`,等于用一个与它们无关的理由宣布它们不可解,连带打红 5 个测试文件。

`validateTrack` 的调用点:生成器测试、`tools/gen-levels.ts`(不合规就让离线构建失败)、`GameController` 里一句 warn(永不阻断游戏)。

1. `track` 是五个已知形状之一(缺失 = `rect`)。
2. `capacity` 是 4 的倍数(8/12/16/20),且在该形状的可用格数内(行距 ∈ [0.70, 1.90])。
3. `boardIndex === capacity / 2`。
4. `feeds` 长度 1 或 2;两条时 side 必须一远一近,不能同侧。
5. 每条 `lookahead` ≥ 1,且 ≤ 该形状按几何算出的前瞻上限(通道最外缘 ≤ 4.67)。
6. 两个入口点的外法线 `|ny| ≤ 0.35`。(这条不是形式主义:六边形 18 格给出 0.569、椭圆 14 格给出 0.578,都是设计期被它拦下来的。)
7. 该形状的最小曲率半径 ≥ 0.6(一行 4 人横排 0.78 宽,弧太急内侧会挤在一起)。

## 性能前置

一个乘客人偶是 **5 个 draw call**(模型导出 5 个材质角色:`paint` / `trim` / `skin` / `eye` / `shoe`)。这一版把最重一关的行数从 18 推到 26:

| | 行数 | 人偶 | 乘客 draw call | 总数 |
|---|---|---|---|---|
| 现在(12 格 + 通道 3×2) | 18 | 72 | 360 | 实测 562 |
| 第 1 关(20 格 + 通道 3×2) | 26 | 104 | 520 | ~720 |
| 合掉 4 个固定角色之后 | 26 | 104 | 208 | ~410 |

所以 **M7 的第一个任务是压 draw call,不是形状**:把 `trim` / `skin` / `eye` / `shoe` 烘成一个顶点色网格(共享材质),`paint` 单独一个(每色一个材质,已有缓存)—— 每人偶 5 → 2。合掉之后总数比现在还低。

按行整体烘焙更省(一行 4 人同色),但一行要沿路径法线扇开、人偶还得保持竖直,烘死的网格做不到 —— 所以走"每人 2 个"这条。

## 测试

core 侧全部进 jest;视图仍然靠预览验收(无测试基架)。

1. 每个形状:闭合、左右对称(镜像误差 < 1e-9)、周长与上表一致、`pointAt(0.5)` 是最低点且 x = 0。
2. 每个形状 × 每个合法格数:行距 ∈ [0.70, 1.90];非法组合(圆形 12 格、六边形 18 格)被 `validateTrack` 拒绝。
3. 两个入口点的外法线 `|ny| ≤ 0.35`,逐形状逐格数。
4. 最小曲率半径 ≥ 0.6。
5. 椭圆折线与解析椭圆的偏差 < 0.001。
6. `validateTrack` 拒绝:未知形状、非 4 倍数格数(14/18)、圆形 12 格、`boardIndex` 不等于半圈、3 条通道、同侧两条、`lookahead` 为 0、`lookahead` 超上限;同一个关卡 `validateLevel` 仍然放行(拆函数的回归网)。
7. `LoopSystem` 单通道:候车全进那一条,另一侧无入口;`reachableColors` 在等价输入下与双通道版一致。
8. 管道拍数用 `step()` 实测(不是复述算式):近端 = `capacity/4`,远端 = `capacity × 3/4`。
9. 10 关全部 `validateLevel` + `validateTrack` 通过 + `isSolvable`,且视野序列与曲线表逐关对上。
10. 无 `track` / `feeds` 字段的关卡回退到 `rect` + 远近双通道 + 前瞻 3,行为与 M6 一致(M6 的死局用例保持绿)。

## 不做的事

- **整关乘客全可见**(真容量通道)。要走这条得把载客量从 16–32 砍到 3–6,难度曲线、生成器、HUD、上车节奏全部重算 —— 单独一个里程碑。
- **通道折线 / L 形 / 从上方进场**。用户明确说不要复杂样式。
- **每关不同的外框尺寸**。外框是相机给的,不是关卡属性。
- **相机 fov 轴换成横向**(真机 19.5:9 适配)。已知问题,与本版无关。
- **道具坞**(package C)。

## 已知风险

1. **第 1 关行距 0.73 偏挤**。在合法区间内(下界 0.70),但 20 格是全套里最密的,只有预览能判断好不好看。退路:第 1 关降到 16 格(行距 0.91)—— 因为格数只能取 4 的倍数,没有中间档。
2. **`reachableColors` 泛化**是死局判定的核心。单通道是新情况(今天永远有两条队列),测试 7 和 10 是这一处的安全网。
3. **第 7 关打破单调**(11 拍 vs 第 6 关末段 5 拍)。刻意的喘息关,但如果玩起来像"变简单了",改成单近端。
4. **梯形通道下倾 15°**。几何上安全(离停车位面板 1.11),但斜着接出去的通道好不好看要看预览。
5. **默认圆角从 0.8 收到 0.60**,今天那个软角的观感会变。0.60 是曲率下界卡出来的,不是挑的。
