# 隧道元素设计文档 (M9)

> 状态:规则已逐条确认(四个决策见下),待用户书面审阅。
> 日期:2026-09-03
> 前置:M8(自由角度驶出)已完成,当前分支 `dev`(`446aebb`)。

## 目标

停车场里多一种元素:**隧道**。隧道是一个固定朝向的**车队列**,队首那辆停在洞口露在外面。玩家点洞口那辆,它就沿隧道的朝向开出去;开走后队伍里下一辆自动补到洞口,再点再开,直到掏空。隧道身上顶着一个数字,写着**里面还剩几辆**。

隧道不是新的解谜维度,是一个**颜色风险源**:里面的车混色,玩家只看得见洞口那一辆,后面是什么色不知道。数字告诉你还要赌几次。

## 需求(用户原话)

> 增加新元素,隧道
> 隧道上显示数字表示隧道内有多少量车

参考图:第 4 关中央一块写着 6 的蓝色方块;引导页写「隧道内的车会逐个移到出口」。

## 已确认的四个决策

- **出车规则**:隧道里的车都是一个朝向。最前面的车走后,后面的车自动补上;再点一下,当前这辆就开走,继续补上,直到出完。
- **障碍与阻挡**:隧道是**硬障碍** —— 别的车开不过去,和一辆停着的车一样挡路。洞口那辆车**按普通车判挡**,被挡就只抖一下。
- **车队成分**:**混色**,玩家只看得见洞口那一辆,后面的颜色是悬念。
- **关卡投放**:**生成器自动排,从第 4 关起**。不手写关卡。

### 一处我自己定的假设

车型固定为 **small**。洞口是一个定尺寸的口子,车型混着会让洞口大小跟着跳。若之后想让大巴也从隧道出来,得先给隧道一个「洞口尺寸」字段,并让保留盒按最大车型算 —— 本轮不做。

## 硬约束

- **core 不认识 Cocos**:`core/` 下任何文件都不许 `import ... from 'cc'`。
- **双闸必须绿**:`cd logic && npm test` 和 `npm run typecheck:view`。
- **可解性由构造保证**:`peel` 产出的剥离顺序就是一个合法解,这条不变式必须活着 —— 隧道加进来以后也要活着(见第三节的论证)。
- **圆环、通道、乘客、停车位一律不动**:`loop-system` / `boarding-system` / `parking-system` / `track-path` / `track-shapes` 零改动。
- 关卡是生成的不是手写的,**不需要向后兼容**;十关全部重新生成并提交 JSON。
- 目标微信小游戏。本轮不碰 draw call 预算,但隧道的模型要和车一样是程序化网格,不引入新资源。

## 一、core 里隧道是什么

### 选定方案:隧道是 `LotSystem` 的一份数据,洞口那辆车是一辆真正的 `CarSpec`

洞口车有 id、有坐标、有朝向、有颜色、有车型 —— 它就是一辆普通车。于是 `GameCore.tapCar`、`LotSystem.canExit`、`ParkingSystem.park`、上客、死局判定、以及 view 的开车动画和车位分配**一行都不用改**:它们根本不知道这辆车是从隧道里来的。

隧道本体只多做两件事:

1. 往 `firstBlocker` 的扫掠里塞一个**静止的盒子**;
2. 在 `LotSystem.removeCar` 里**补位** —— 拿走的是某隧道的洞口车,就当场发下一辆,新 id。

**赢/死局条件不用动**。隧道没掏空,洞口就永远有一辆车在 `lot.cars` 里,`isEmpty()` 自然为假;洞口车能不能开由 `movableCarIds()` 照常回答。这条不变量是白捡的,不需要在 `game-core.ts` 里加任何一行。

### 否决的两个方案

- **隧道自己是可点对象**(`tapTunnel(id)` 走一条平行链路)。开车动画、车位分配、上客、死局都要写第二遍,而 `GameController` 已经 2087 行。两条链路一旦分岔就再也合不回去。
- **生成时摊平成 N 辆叠在洞口的车**。直接违反 `validateLevel` 的间距校验,以及 `move-solver.ts` 里写明的「扫掠开始时没有任何一对车重叠」这条载重不变量 —— 那条不变量在的时候 `firstBlocker` 报的 gap 才恒为正。

### 几何:隧道体在后,洞口车在前

隧道体的盒子在**后**,洞口车紧贴在它**前面**,两者相距一个 `CLEARANCE`。别的车撞上隧道体就停;洞口车朝前开,身后的隧道对它不构成阻挡 —— 这不是巧合,是 `geometry.ts` 的 `sweepHit` 写明的行为:**接触在车身后方一律返回 null**(「A car does not reverse into the car behind it」)。

```
        隧道体(len = TUNNEL_LEN)      洞口车(small)
   ┌──────────────────────────┐  ┊  ┌─────────┐
   │                          │  ┊  │  ← 车头 │ ──→ angle
   └──────────────────────────┘  ┊  └─────────┘
                              CLEARANCE
```

隧道的 `x, y` 记的是**隧道体的中心**,`angle` 是出车方向(0° = +X,逆时针,`[0, 360)`,和车一致)。洞口车的中心由 `angle` 推出来,不单独存 —— 存两份就会有两份不一致的可能。

### 类型

`game/assets/scripts/core/types.ts`:

```ts
/** 隧道里排队的一辆车:除了颜色和车型,其余(位置、朝向、id)由隧道决定。 */
export interface TunnelCar { color: string; cap: Cap }

/**
 * 一条隧道。`x`/`y`/`angle` 描述的是隧道**本体**;洞口车的位置由本体推出。
 * `cars[0]` 是当前露在洞口的那辆,数组随出车从头部消耗。
 */
export interface TunnelSpec {
  id: number;
  x: number;
  y: number;
  angle: number;
  cars: TunnelCar[];
}

/** 隧道本体的尺寸,板单位。`len` 沿 angle,`wid` 横过它。 */
export const TUNNEL_BOX: Box = { len: 1.2, wid: 0.76 };
```

`LevelData.lot` 加一个可选字段 `tunnels?: TunnelSpec[]`。可选,所以 core 测试里那些合成关卡一个字不用改。

`wid` 0.76 = small 车宽 0.471 加两侧各 0.145 的洞壁,车从里面滑出来时两边看得见墙。`len` 1.2 略多于一个车长,所以数字牌下面有块实在的顶,而不是一个薄片。和 `CAP_BOX` 一样由 core 持有,view 从 core 读 —— 不在 view 里另存一份。

这对场地密度基本中性:一条隧道的保留盒吃掉 2.44 板单位²(见第三节,两头都留洞口车位),而它换走的 4 辆小车占 1.82(4 × 0.454)。差额 0.6 相当于 1.3 辆小车,落在 8 × 10 = 80 的场地上是 0.75%。所以 `CARS_PER_LEVEL` 和 `CAR_SCALE` 都不用动。

### 车 id 的发号

隧道的车必须和网格车共用一个 id 空间(`parking.park` 存的是 `carId`,`onDeparted` 按 id 找节点)。约定:**网格车用关卡 JSON 里写死的 id;隧道车的 id 由 `LotSystem` 在运行时发**,从 `max(网格车 id) + 1` 起递增。这样关卡文件里不必为还没出场的车预留号段,而 id 依然全局唯一。

## 二、core 的改动清单

### `move-solver.ts`:多认一组静止盒子

```ts
export function firstBlocker(
  car: CarSpec, cars: CarSpec[], lot: Lot, blockers?: OBB[],
): Blockage | null
```

`blockers` 是纯 `OBB`,不是 `CarSpec` —— 隧道体没有颜色、没有容量、不能被点,把它伪装成一辆车会让每一处「车」的遍历都要记得过滤掉它。`Blockage.carId` 对隧道体报什么?加一个字段更诚实:

```ts
export interface Blockage {
  /** 挡路的车;被隧道体挡住时为 -1。 */
  carId: number;
  gap: number;
}
```

只有 view 的提示文案在乎这个区分(「被那辆车挡住」vs「隧道挡着」),`pathClear` 不在乎。broad-phase 的 `perp` 剪枝对静止盒子同样适用,照抄即可。

### `lot-system.ts`:持有隧道,并在 `removeCar` 里补位

```ts
export class LotSystem {
  bounds: Lot;
  cars: Map<number, CarSpec>;
  tunnels: TunnelSpec[];

  /** 隧道体的盒子,构造时算一次。`canExit` 每次把它传给 pathClear。 */
  private blockers: OBB[];
}
```

- 构造时:为每条隧道把 `cars[0]` 实例化成一辆真车放进 `this.cars`,并把隧道体的 OBB 存进 `blockers`。
- `removeCar(id)`:删掉车之后,若这个 id 是某条隧道的当前洞口车,就 `shift()` 掉 `cars[0]`,若队列还有剩,把新的 `cars[0]` 实例化到洞口。
- `canExit` / `movableCarIds`:照旧,只是把 `blockers` 一起传下去。

补位是**同步**发生的 —— core 里没有动画,洞口车在上一辆被移除的同一次调用里就换好了。view 那边的滑出动画是纯表现,期间 core 已经认为新车在洞口了。这一点和现有的 `ParkedCar.ready` 是同一个模式(core 立刻,view 慢慢演),但方向相反:那边是 view 需要一个「还没到位」的标记,这边**不需要** —— 洞口车滑出期间即使被点,判挡的结果也和滑出结束后一样,唯一的差别是动画会被打断。view 用一个本地的「滑出中」标记吞掉这段时间的点击即可,不必污染 core。

### `level-data.ts`:`validateLevel` 加五条

1. 每条隧道的本体盒子完全在场内(`insideRect`);
2. 隧道本体与**每一辆网格车**满足 `CLEARANCE`(各摊一半,和车与车之间同一套算术);
3. 隧道之间也满足 `CLEARANCE`;
4. **洞口车位**不与任何网格车、任何别的隧道本体重叠 —— 洞口车是从第 0 帧就存在的实体,它的位置必须像一辆停着的车一样合法;
5. `cars` 非空(空隧道是数据错误,不是「已掏空」—— 掏空是运行时状态,不该写进关卡文件)。

「车容量 == 乘客数」这条老约束的分子要**把隧道里的车算进去**。这是最容易漏、漏了直接炸的一条。

### `solvability.ts`:`clearGrid` 改跑 `LotSystem`

现在它跑的是裸数组 `level.lot.cars.slice()`,看不见隧道会吐新车。改成构造一个 `LotSystem`,每轮取 `movableCarIds()` 全部移除(补位自动发生),下一轮再来。

- 终止性:每轮至少移除一辆,而车的总数(网格车 + 所有隧道里的车)是有限的;一轮一辆都移不动就是死局,返回 `cleared: false`。
- `rounds` / `blocked` 的含义不变,`estimateDifficulty` 的公式不动 —— 但分数会因为多了隧道车而整体上移,这是应该的。

## 三、生成器

### 顺序:隧道先落位,车再绕着它排

1. **隧道落位**:在场内随机选中心点和**轴线**,占一个**对称保留盒** —— 本体居中,两端各留一个洞口车位:

   ```
   len = 1.2 + 2 × (0.04 + 0.964) = 3.208     wid = 0.76
   ```

   整个保留盒必须 `insideRect`,且与别的隧道的保留盒隔一个 `CLEARANCE`,否则重抽。
2. **`pack`**:松弛照跑,但隧道是**不动的刚体** —— `overlapMTV` 命中时只推车,不推隧道,也不对隧道调 `clampInside`。
3. **定朝向**:`pack` 之后,从 `axis` 和 `axis + 180` 两个朝向里挑一个 —— 优先挑让洞口车**初始通畅**的那个。
4. **`peel`**:隧道本体作为静止障碍参与 `pathClear`,所以剥离顺序在有隧道的场地上依然是一份真解法。

**保留盒为什么是对称的。** 只留一头(`1.2 + 0.04 + 0.964 = 2.204` 长)更省地方,但那样朝向就得在 `pack` **之前**定死,而洞口通不通畅要 `pack` 完才知道 —— 一条随机朝向的隧道在 80% 密度的场地里开局被焊死的概率不低,而一条点不动的隧道挂着数字 6 看着就是个 bug。两头都留,朝向就能在 pack 之后二选一,命中率翻倍。

代价是每条隧道多吃 0.77 板单位²(约 1.7 辆小车)。这个做法不是新发明:`headingsFor` 对每辆车做的就是同一件事 —— **先把地方占住,朝向留到最后再定**,因为矩形转半圈盖住的是同一块地。

### 可解性是白送的

不需要为隧道做拒绝采样。论证一行:

> `peel` 保证网格上的车最终全被拿走;拿光之后,隧道出口射线上什么都没有了(隧道本体在洞口车**身后**,`sweepHit` 对身后接触返回 null);所以隧道那 N 辆车最坏也能在最末尾逐辆开出。

于是**任何通过 `validateLevel` 的摆放都可解**。实际玩起来通常中途就能掏,那是白赚的,不需要保证,也不该去保证 —— 保证它就要在 peel 里插入隧道车的时机,而那会让「剥离顺序即解法」这条不变式变成一个需要论证的复杂命题。

### 朝向择优:交给现成的 `ATTEMPTS` 循环

随机朝向可能一开始就被一堆车焊死,数字 6 挂在那儿点不动,看着像 bug。

不需要为此新建一套挑选逻辑 —— `generateLevel` 已经跑 `ATTEMPTS = 200` 次整关尝试,按 `miss` 取最好的那次。隧道的位置和朝向是每次尝试各抽一份的,所以只要把「**开局时有几条隧道的洞口车是被挡的**」加进那个打分里(权重高于 `miss`,因为一条点不动的隧道比差一辆车严重),200 次里挑出全部通畅的那一次是件很容易的事。

打分而不是硬性拒绝:洞口初始被挡的关卡**仍然可解**(见上一小节的论证),只是手感差。留成打分项,意味着极端情况下生成器不会因为挑不出完美摆放而整关失败。

### 曲线与预算

| 关卡 | 隧道数 | 每条车数 |
|---|---|---|
| 1~3 | 0 | — |
| 4~6 | 1 | 4 |
| 7~8 | 2 | 5 |
| 9~10 | 2 | 6 |

- **每关总车数仍是 60**,隧道里的车从这 60 里出 —— 第 4 关是 56 辆网格车 + 4 辆隧道车,第 9 关是 48 + 12。不这样的话乘客总数和难度曲线会跟着跳,而那两条曲线是调过的。

写进 `levelParams` 旁边一张新表 `TUNNEL_CURVE`,和 `TRACK_CURVE` 一个位置、一个写法。

### 隧道车的染色

`choosePainting` 现在在网格车的剥离顺序上搜索配色。隧道车不在那个顺序里(它们的出场时机不由 peel 决定),所以简单处理:**隧道车的颜色从关卡已有的调色板里随机抽**,抽完之后 `queueFor` 照单全收 —— 乘客数是从车推出来的,不是反过来,所以怎么抽都不会破坏平衡。

「混色、只看得见洞口那一辆」正是这个机制想要的效果,不需要更聪明的算法。

### 必须重跑 gen

关卡 JSON 的格式变了。按 README 那条约定,**改完必须 `npm run gen` 并把 10 个 JSON 一起提交**,否则运行时的关卡和代码里的规则对不上。

## 四、表现层

- **`view/tunnel-mesh.ts`(新)**:和 `car-mesh.ts` 一样程序化生成 —— 一个带厚度的拱(半管),正面开口朝 `angle` 方向,背面封死。不引入新资源。
- **数字牌**:一块圆角底 + 一个 `Label`,活在 **HUD 层**,每帧放到隧道中心投影到屏幕的那个点上 —— `cam.worldToScreen` → `uiCam.screenToWorld`,和 `placeSpeedButton`、`positionChip` 走的是同一条路。

  一开始想的是「挂在棋盘节点下、反向抵消 `BOARD_TILT`」,那要让一个 `Label` 在 3D 节点上渲染,而这个项目里所有文字都在 Canvas 下;HUD 这条路已经有两处在用,不引入新的渲染路径,也天然正对镜头。代价是数字牌不被任何 3D 物体遮挡 —— 对一个永远该看得见的读数来说这不是代价。

  数字 = 隧道里**还没开走的总数**(含洞口那辆),洞口车一开走就减 1。
- **补位动画**:洞口车开走后,下一辆从隧道肚子里**滑出来**(一段短平移 + 淡入),不能瞬移 —— 瞬移会让玩家以为是同一辆车没走掉。滑出期间这辆车不可点(view 本地标记,不进 core)。
- **调试叠加层**:按 D 键时把隧道本体的盒子也画出来,用第三种颜色(绿=能出,粉=被挡,新增一种=静止障碍)。否则「core 认为哪儿被挡」这件事会有一块看不见,而 README 把这个叠加层当成表现层 bug 的唯一判据。
- **`GameController`**:`buildBoard` 里多建隧道节点;`onDeparted` 之后触发补位动画。tap 链路、开车动画、车位分配**零改动** —— 这是第一节选定方案换来的。
- **编辑器**:`editor/` 至少要能读带 `tunnels` 字段的 JSON 不崩。**能不能编辑隧道,本轮不做**。
