## 1. 要解决的问题

四条需求:

1. 每日签到领金币,**按日期签到**
2. 过关获得金币,不同星级不同
3. 金币可以用来**解锁车位**
4. 要有金币的**收支记录**

其中第 2 条已经存在,第 1 条存在但形态不对,第 3、4 条完全没有。

### 1.1 但真正的问题是第 3 条会把现有代码咬坏

`wallet.ts` 的 `backfilledWallet` 每次开机都跑,把余额抬到"按当前星级本该发过的总额"。它自己的注释写着 `RAISES, NEVER LOWERS`,而这条规则成立的**前提是金币只进不出**:

> A balance ABOVE the derived figure is not a bug to correct -- it is coins from a source
> that is not progress.

一旦金币能花出去,前提就没了。玩家花 80 币开了车位,下次开机余额低于派生值,**系统把钱退还给他**。花钱变成免费,消费端整个失效。

所以这不是"顺便修一下"的细节 —— 它是第 3 条需求的必答题,也是这次要把存档模型整个换掉的原因。

### 1.2 现状盘点

| 件 | 现状 |
|---|---|
| 余额 | `Wallet { version, coins }`,存的是一个数 |
| 赚币 | 过关按最佳星级累进发放 `[0,25,40,60]`,差额制;签到 7 天循环 `[20,20,30,30,40,40,100]` |
| 花币 | **没有任何出口** |
| 解锁车位的代价 | **星星**,不是金币:`stars() = max(1, STAR_MAX - unlocksUsed())` |
| 流水 | 没有 |
| 签到模型 | 连签第几天 + 断签归零,界面上没有日期概念 |

### 1.3 一条核对结果:金币不会卡住进度

`level-gen.ts:1831` 有 `if (v.demand > UNLOCKED) continue` —— 生成器已经把"必须买车位才能通关"的候选全部淘汰了。每一关都能在开局那 4 个车位上、一分钱不花地通关。

这条让「余额不足就把按钮置灰」成为一个安全的选择:买车位是救场,不是通关必需,置灰不会让任何人卡在任何一关上。**这是本设计里唯一一条依赖生成器行为的假设,改动生成器时要回头看这里。**

## 2. 决策与取舍

### 2.1 解锁形态:关内临时,不是永久

金币开的是**本局**的车位,换关回到初始 4 格。不做"永久提升开局车位数"的商店 —— 那是另一套定价和另一套 UI,且会让所有关卡的难度曲线整体位移,而难度曲线是 `demandTarget` 精心校过的。

### 2.2 代价:金币 + 星星双重

开一格既扣金币,也照旧掉一星。

不取消星星代价,是因为**过关金币是按星级发的**。解锁若不再掉星,`stars()` 恒为满分,每关都发 60 币,赚币端的强弱之分当场消失 —— 那就得另起一套评星标准(耗时?步数?)并重新校准 10 关的阈值,代价远大于收益。

双重代价还自带一个天然的负反馈,不需要额外设计:买它的钱,同时也买掉了它未来能赚回的钱。

### 2.3 余额不足:置灰,引到签到

不做首次免费,不做保底派发。生成器已经保证了不会卡关(见 1.3),所以诚实置灰是可以接受的;多一条派发规则就多一处要记账、要防刷的地方。

### 2.4 签到:月历式,断签不清零,无补签

本月日历网格,签过的日子打勾,按"本月累计第 N 天"发奖,跨月整份重置。

断签不清零 —— 月历模型里没有"连续"这个概念,漏签就是少领一天。不做补签:那是第二个金币出口,和第一个出口的定价会互相牵制,等有了更多消费场景再谈。

### 2.5 架构:流水账是唯一真相

三个方案:

- **A. 余额由流水算出** — 结构上不可能对不上
- **B. 余额单独存,流水只是旁证** — 改动最小,但同一个事实存两份
- **C. 钱包 + 流水 + 签到合并成一个键** — 最省 IO

**选 A。** 理由不是优雅:这次"要能花钱"和"要有流水"是同时来的,B 方案下这两件事各自正确、合起来可能不一致 —— 而单机游戏没有任何对账机制能发现这种不一致,它只会表现为玩家看到一串解释不了当前余额的明细,且只能靠肉眼发现。A 把它变成结构上不可能。

否掉 C 的理由具体:签到和钱包的生命周期规则在 `storage.ts` 里被专门论证过是分开的两件事,合并会把那段论证作废;且签到的月历改版会连带钱包一起 version bump,两次无关的演进被绑死。

A 的代价说清楚:所有增减必须走同一个入口,不能再有人直接 `coins + n`。

## 3. 数值

### 3.1 三张表

```
解锁单价(本局内第几次,换关重置)   UNLOCK_PRICES  = [20, 40, 80]
过关奖励(按最佳星级累进,差额发放)  COIN_FOR_STARS = [0, 25, 40, 60]
签到奖励(本月累计第 N 天)          CHECKIN_REWARDS[(N - 1) % 7]
                                   CHECKIN_REWARDS = [20, 20, 30, 30, 40, 40, 100]
```

后两张沿用现有数值,只有取值方式变了(签到从"连签第几天"变成"本月第几天")。本月第 7/14/21/28 天各有一次 100。

单价递增而非固定,是为了让第一次救场便宜到人人买得起(否则置灰弹窗天天出现),第三次贵到让人宁可重开 —— 固定价做不出这个梯度。

### 3.2 首通一关的净收支

| 开了几格 | 星级 | 过关得 | 解锁花 | 净 |
|---|---|---|---|---|
| 0 | 3 | 60 | 0 | **+60** |
| 1 | 2 | 40 | 20 | **+20** |
| 2 | 1 | 25 | 60 | **−35** |
| 3 | 1 | 25 | 140 | **−115** |

开一格还能小赚,开两格开始肉疼,开三格是明确的败家。这是想要的形状。

### 3.3 重玩不产币,但仍扣币

过关奖励是差额制,重玩已三星的关卡拿 0 币 —— 这堵死了刷币。副作用是重玩时开车位照样扣钱,净亏。

这是正确的,但玩家会困惑,所以要说明。**说明放在过关结算面板上**("已是最好成绩 · 无金币奖励"),不放进流水:零额不入账(见 4.2),而且结算面板上玩家的注意力正在那里,比事后翻明细更早、更准。

### 3.4 一条明示假设:内容体量

全游戏当前 10 关,终身产出上限 `10 × 60 = 600` 币;月历签到满月约 1120 币。仅以当前关卡数计,第二个月起余额只增不减,20/40/80 的定价会失去意义。

**已确认后续会增加关卡**,消费端会随内容一起长,因此本次不调数值。若关卡数长期停在 10 关附近,旋钮有两个:签到降档(砍掉 100 那档,日均约 25),或给金币加第二个出口。

## 4. 存档模型

### 4.1 `core/wallet.ts` → v2

```ts
export const WALLET_VERSION = 2;
export const LEDGER_MAX = 100;

export type CoinReason = 'clear' | 'checkin' | 'unlock' | 'carryover';

export interface LedgerEntry {
    t: number;       // Unix ms
    why: CoinReason;
    n: number;       // 带符号:收入为正,支出为负,永不为 0
    ref: number;     // clear/unlock:关卡号;checkin:本月第几天;carryover:0
    extra?: number;  // clear 专用:本次星数。其余 why 不写
}

export interface Wallet {
    version: number;
    opening: number;       // 最老一条流水之前的结余
    log: LedgerEntry[];    // 最旧在前,最多 LEDGER_MAX 条
}
```

**不变式:`balance(w) === w.opening + sum(log.n)`,且恒 ≥ 0。**

超出 `LEDGER_MAX` 时,从最老一端**逐条**折进 `opening` 再丢弃,直到长度回到上限 —— 明细滚掉了,钱一分不少,不变式不破。逐条而非批量,是因为每次只追加一条,循环至多走一轮;写成循环而不是"丢掉第一条"则让这段代码对一份长度已经越界的存档(旧版本、手改)也是对的。

### 4.2 为什么是 `earn` / `spend` 两个函数,不是一个带符号的 `apply`

```ts
export function balance(w: Wallet): number;
export function earn(w: Wallet, why: CoinReason, n: number, ref: number, now: number): Wallet;
export function spend(w: Wallet, why: CoinReason, n: number, ref: number, now: number): Wallet | null;
```

分成两个,是让符号在调用点不可能写反 —— 一个 `apply(w, -20)` 和一个 `apply(w, 20)` 看起来一样对。

`spend` 在余额不足时返回 `null` 而不是抛错、也不是静默返回原钱包:返回原钱包会让"钱不够还继续开了车位"变成一个不报错的 bug;抛错则要在 UI 的点击路径上加 try/catch。`null` 是调用点无法忽略的。

两者都不改传入的钱包 —— 和现有 `addCoins`、`recordClear`、`claim` 同一条约定:调用方持有它作为当前状态。

`n` 非正整数、非有限数(0、负数、小数、`NaN`、`Infinity`)时**不产生流水行**,并返回**传入的那个对象本身** —— 一条 `n: 0` 的记录既不是收入也不是支出,只会污染明细。返回同一个对象而非一份拷贝,是沿用 `backfilledWallet` 已经在用的约定:调用方可以用 `===` 判断"什么都没发生",从而决定要不要写盘。`GameController` 的差额制发币路径正需要这个 —— 重玩拿 0 币时不该产生一次同步写入。

`spend` 的 `n` 同样只接受正整数:它自己在内部取负,调用点**永远传正数**。这是 4.2 开头那条"符号不可能写反"的另一半。

### 4.3 v1 迁移与回填的收口

`parseWallet` 的三条路径:

| 读到 | 结果 | 是否回填 |
|---|---|---|
| `version === 2` 且合法 | 原样 | **否,永不** |
| `version === 1`(`{version, coins}`) | `{version:2, opening: coins, log: []}` | **是,一次** |
| 缺失 / 损坏 / 其他版本 | `emptyWallet()` | **否** |

回填保留 `coinsFromProgress` 的推导(它是纯的、已被测试钉住),但**只在 v1 路径上跑一次**:取 `max(旧余额, 派生值)`,差额记一条 `carryover`。写成 v2 之后,`backfilledWallet` 再也不会被调用 —— 1.1 那个退款 bug 就此消失。

损坏的 v2 存档归零且**不**回填,是刻意的:若损坏也触发回填,手改存档就成了退款按钮。代价是损坏存档的玩家丢掉余额 —— 和现有政策一致(`parseWallet` 今天就是这么做的)。

`parseWallet` 因此需要把"是否来自 v1"告诉调用方。签名改为返回 `{ wallet: Wallet; fromLegacy: boolean }`。

### 4.4 `core/checkin.ts` → v2

```ts
export const CHECKIN_VERSION = 2;

export interface Checkin {
    version: number;
    month: string;     // 'YYYY-MM'
    days: number[];    // 本月已签日,升序,1..31,无重复
}
```

- `canClaim(c, today)`:`today` 的月份不是 `c.month`,或其日不在 `c.days` 里
- `claim(c, today)`:跨月则整份重置为 `{month, days:[d]}`,否则插入并保持升序;付 `CHECKIN_REWARDS[(days.length - 1) % 7]`,`days.length` 取**插入之后**的值
- `nextReward(c, today)`:`claim` 会付多少
- `claimedDays(c, month)`:给月历网格画勾用

`nextDay`、`yesterdayOf` 与整套连签逻辑删除 —— 月历模型里没有"连续"这个概念。

`todayKey` 保留,连同它那段"用设备本地时区而非 UTC"的论证,理由一字不改。新增 `monthKey(now)` 与 `dayOf(todayKey)` 两个纯函数。

**v1 迁移**:v1 的 `{day, last}` 里,`day`(连签位置)在新模型中无处可去,也不该再有。只保留 `last`:若它解析得出且属于当月,则 `{month: monthOf(last), days: [dayOf(last)]}`,否则 `emptyCheckin()`。这一步唯一的作用是防止"更新当天重复领一次"。

### 4.5 存档键与生命周期:不变

`parking.wallet` 与 `parking.checkin` 两个键名都不改 —— 版本号在 payload 里,是项目既有约定(`PROGRESS_VERSION` 的注释论证了为什么不放进键名)。

两者随进度清除的规则也不变,`storage.ts` 里 `clearWalletText` 和 `clearCheckinText` 那两段论证原样成立:金币由游玩产生,签到记录也是,两者都不该越过一次清档活下来。

### 4.6 写盘时机

现有纪律是"只在过关时写一次"。新增一处:**关内解锁扣费要立即写盘**。

这是一次玩家主动点击、且弹窗已经挡住全屏时的同步写入,每关至多 3 次,不在每帧路径上。不写盘的代价是玩家开了车位后杀进程就白嫖一格,那正是这次要堵的洞。

### 5.2 流水面板

点顶栏金币药丸弹出 —— 那个药丸今天是"画出来但故意无效"的控件(`TopBar.coinTap` 的注释),这次给它真正的职责,不新增任何图标。

顶部大字余额,下面最多 100 条明细,每行 `09-22 · 第 3 关 三星 · +60`。事由文案由 `why` + `ref` 拼出:

| `why` | 文案 |
|---|---|
| `clear` | `第 N 关 三星 / 二星 / 一星` |
| `checkin` | `签到 第 N 天` |
| `unlock` | `第 N 关 开车位` |
| `carryover` | `往期结转` |

`clear` 那行要印星级,而星级**不能从 `n` 反推** —— 差额制下一笔 `+15` 既可能是二星升三星,也可能是别的差额。所以 `LedgerEntry` 带一个可选的 `extra`(见 4.1),`clear` 用它存本次星数,其余 `why` 不写这个字段。

不选"把 `level * 10 + stars` 编进 `ref`"的原因很实际:那会让 `ref` 在不同 `why` 下含义不同,而它已经在 `checkin` 上是"本月第几天"、在 `unlock` 上是关卡号了。再叠一层编码,解码逻辑就得按 `why` 分叉,而分叉点每多一个,就多一个能写错的地方。

### 5.3 签到卡改月历

现有 7 格换成当月日历网格(最多 6 行 × 7 列):已签打勾、今天高亮、未来置灰、上月遗留的空格留白。底部「领取 +N」按钮,`canClaim` 为假时置灰。

哪一格可领、领多少,都从 core 读(`canClaim` / `nextReward`),不在 view 里重算 —— 这条是现有代码已经论证过的纪律(`paintCheckin` 的注释),月历版照搬。

### 5.4 解锁弹窗

`UnlockCost` 增加两个字段:

```ts
export interface UnlockCost {
    left: number;        // 还能开几个,含这一个
    losesStar: boolean;  // 开这一个是否真的掉星
    price: number;       // 这一个要多少币
    affordable: boolean; // 现在买不买得起
}
```

- 买得起:`还能开 N 个 · 20 币 · 少一颗星`
- 买不起:按钮置灰,`金币不足 · 还差 15`

买不起且**今天还没签到**时,并排多一个「去签到」,把签到卡叠在弹窗之上(复用现有 `supersedeSettings` 的层叠套路),领完退回弹窗、按钮自动变亮。

今天已签过则**不给**这个按钮,只写一行 `明天签到可得 N 币` —— 一个点了没用的按钮比没有按钮更糟。

### 5.5 过关结算面板加一行金币结果

`showWin` 的面板上多一行,三种状态:

- 有奖励:`金币 +40`
- 重玩且未破纪录:`已是最好成绩 · 无金币奖励`
- 本局花过币:上面那行之后再加 `开车位 −60`,让净额自己说话

第二条是 3.3 那个困惑的正解:玩家刚打完、注意力就在这块面板上,此刻告诉他比让他事后去翻明细早得多。第三条把"这局到底是赚是亏"摆在同一屏,而不是让他去做减法。

## 6. 测试

core 全部可测(不 import 'cc'),jest 覆盖:

**wallet**
- `balance` 不变式:任意 `earn`/`spend` 序列后,余额恒等于 `opening + sum(log.n)`
- 第 `LEDGER_MAX + 1` 条进来:最老一条折进 `opening`,余额不变,长度仍为 `LEDGER_MAX`
- `spend` 透支返回 `null`,且不改动传入的钱包
- `earn`/`spend` 的 `n` 为 0、负数、小数、`NaN`、`Infinity` 时不产生流水行
- v1 迁移:`{version:1, coins:N}` → opening N,`fromLegacy` 为真
- 损坏 / 缺失 / 未知版本:空钱包,`fromLegacy` 为假
- `backfilledWallet` 取 `max(旧余额, 派生值)`,且派生值不高于旧余额时返回同一个对象
- `UNLOCK_PRICES` 按 `unlocksUsed()` 取值:第 0/1/2 次分别为 20/40/80;索引越界时取**表尾值 80**(当前关卡数据下 `slots - unlocked === 3`,第 4 次不可能发生,但取表尾让这条对任何关卡数据都成立,而不是 `undefined`)

**checkin**
- 跨月:上月 20 天的存档在新月第一天签到,`days` 重置为 `[1]`,付第 1 天的钱
- 同日重复:`canClaim` 为假
- 断签:本月签了 1、2、5 号,5 号付的是"第 3 天"的钱,不是"第 5 天"
- `(N-1) % 7` 的绕回:本月第 7、8、14 天分别付 100、20、100
- v1 迁移:`last` 属于当月则种下那一天;`last` 为空或属于上月则空存档
- 月末边界:31 日签到,`days.length` 上限不越界
