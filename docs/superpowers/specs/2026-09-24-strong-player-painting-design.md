## 1. 要解决的问题

人类伙伴反复报告同一件事:**"只用了三个车位,感觉甚至两个车位都可以。"** 而生成器给每一关的判定都是"需要满四个车位"。

这两个说法不可能同时对。这次的测量说明是生成器错了:它判断难度用的是 `play-sim.ts` 里三个机器人(`decisive`、`careful`、`keepDistinct`),而它们比人弱得多,**弱在一个具体的地方:只看颜色,不看停车场结构**。它们从不考虑"先开走 A,能把后面被 A 挡住的 B 放出来"——这恰恰是挪车游戏里人最常做的规划。

### 1.1 证据一:机器人的车位需求和真实需求对不上

在 scratchpad 里写了一个会往前看的玩家(每次点车前把每个选项分叉出去推演到终局,选推演结果最好的那个),用它打**出货的**九关,车位限制到 3 个和 2 个、不许买:

| 关 | 3 车位:机器人组输时剩余乘客 | 3 车位:往前看的玩家 | 2 车位:往前看的玩家 |
|---|---|---|---|
| 2 | 232 | 过关 | 232 |
| 3 | 272 | 过关 | 过关 |
| 4 | 624 | 过关 | 过关 |
| 5 | 416 | 过关 | 过关 |
| 6 | 304 | 过关 | 过关 |
| 7 | 416 | 280 | 296 |
| 8 | 416 | 过关 | 过关 |
| 9 | 704 | 过关 | 440 |
| 10 | 676 | 过关 | 过关 |

机器人组三个车位一关都过不了;往前看的玩家三个车位过八关,两个车位过六关。第 4 关两个车位能过,和人类伙伴当初"两个车位连过四次"的报告吻合。**出货关卡标的"要四个车位"是机器人的需求,不是关卡的需求。**

### 1.2 证据二:机器人判的"死局"大多不是死局

`judge().dead` 的定义是"三个机器人买满车位也没一个赢"。用往前看的玩家复核机器人判死、且比出货配色更窄的候选:

| 关 | 400 个候选里机器人判死 | 复核最窄的 6 个 | 能过 | 其中三星 |
|---|---|---|---|---|
| 3 | 16 | 6 | 6 | 6 |
| 7 | 77 | 6 | 6 | 4 |
| 10 | 180 | 6 | 6 | 2 |

18 个没有一个是真死的。第 10 关近一半候选被机器人错误地扔掉,而被扔掉的恰恰是最窄的那一批。

### 1.3 证据三:换了尺子,池子里确实有更难的配色

在机器人判为存活的配色里,比较两种尺子给出的车位需求:

- 第 4 关:最窄的存活配色(width 2.23)强玩家要 **3** 个车位,出货那个只要 2 个;机器人判"要 4 个"的那个(3.44)强玩家 2 个就过。
- 第 10 关:存活配色里强玩家的需求全是 1 或 2,但最窄的(2.26)比出货(2.70)窄 0.44。

机器人的车位判断和强玩家的几乎没有相关性。生成器现在按 `|demand − 4| × 100 + width × 10` 排序,等于在对着噪声凑数。

### 1.4 已排除的方向(同一天测过,不要再绕回去)

| 方向 | 结果 |
|---|---|
| 单关加颜色(7、8 色) | width 2.64 → 2.86,更容易:颜色多了,每色车少,色块变短 |
| 去掉形状、加车到 76 辆 | width 5.17:同时能开走的车从约 4 辆涨到 9.2 辆,吃掉了色块变长的收益 |
| 扩大配色搜索预算 | width 2.64 → 2.61,不是瓶颈 |

### 1.5 测量工具的一个错误(记在这里,免得重犯)

当天前半段的几个"死局"实验是错的:脚本只改了车的颜色,没有重建乘客队列。队列是 `assemble` 用 `bandedQueue(cars, tunnels, offset, interleave)` 从车的颜色和离场顺序现推出来的,换色不重建,乘客就有一部分没有对应颜色的车可坐,必输。**任何对配色做实验的脚本,都必须走和 `assemble` 相同的队列重建。**上面 1.2、1.3 的数据都是修正之后重测的;1.1 用的是出货关卡原样,不受影响。

## 2. 设计

### 2.1 新模块 `core/search-player.ts`

纯逻辑,不 import `cc`,与 `play-sim.ts` 同层。

**`forkCore(core: GameCore): GameCore`**
复制一局的完整状态。结构化深拷贝:保留原型(`Object.create(Object.getPrototypeOf(x))`),用一张备忘表保证共享引用仍然共享(`BoardingSystem` 同时指向 `LoopSystem` 和 `ParkingSystem`),Map、Set、数组分别处理。core 的各个系统里没有闭包属性、没有类型化数组,这种拷贝是完整的。

**`searchPlay(level, { buy, seed }): Playout`**
往前看的玩家打一整局,返回值与 `playOut` 同型。tick 循环与 `play-sim.ts` 的 `play` 保持同一套规则(每拍先点车、每个空车位最多点一辆、再走一拍;`buy` 时卡住就买车位)。每次要点车时:

- 选项 = 每辆当前能开出去的车,加上"这一拍不再点"。
- "不再点"只在环上还有空格时才提供——环满时等待不会改变任何东西,这与 `decisive` 的判断一致。
- 每个选项分叉出去,用 8 条推演线打到终局:`decisive`、`careful`、`keepDistinct` 各一条,另 5 条是 `slip(decisive, 0.15–0.25)` 配不同种子。
- 选项的分数取**最好的那条线**(只需要一条路能过),平均值只作极小的平手判据。
- 推演线打分:赢 = 1000 − 50 × 买的车位数;卡死 = −剩余乘客数;跑到 tick 上限仍未结束 = −剩余乘客数 − 500(那是原地空转,不是差一点)。
- 打平时优先点车。"不再点"必须严格更好才被选中。这条是在 scratchpad 里踩过的坑:早期版本打平时停在"等待"上,九关全部空转到 tick 上限。

所有随机数由传入的 `seed` 派生,不用 `Math.random`,不读时间。同一关、同一种子,结果完全确定。

**`certifyThreeStar(level, salt): boolean`**
用 `level.parking.unlocked` 个车位、不买,最多换 3 个种子打。**任何一局赢了即通过。**赢是确凿证据:它真的走出了一条不买车位的通关路线。

**`strongDemand(level, salt): number`**
前提是已通过三星认证。依次试 3、2、1 个车位,每档最多 3 个种子;某档有一局赢就继续试下一档,某档三局都输就停,返回上一档的车位数。

必须写进注释的一点:**输不是证据。**同一个配色,出现过"四车位不买输了、允许买却 0 个车位赢了"的情况——它是启发式搜索,不是穷举。所以 `strongDemand` 是真实需求的**上界**,多试几个种子是为了把这个上界压实一点。

### 2.2 `choosePainting` 的第二遍

第一遍不变:400 个配色,每个只数颜色算 `frontierWidth`,零模拟,按 width 升序排好。

第二遍改为:

```
for 候选 in 按 width 升序:
    if 本关已用对局数 >= GAME_BUDGET: break
    level = assemble(id, 重新上色的车, tunnels)        // 队列随车重建
    if not certifyThreeStar(level): continue           // 证明不了三星,不交给玩家
    d = strongDemand(level)
    if d == 目标(DEMAND_CURVE): return 这个配色          // 需求顶到目标,又是目前最窄的,最优
    收入候选(d, width)
    if 已收入 >= ACCEPT: break
return 已收入里 |d − 目标| 最小者,同分取 width 最窄;一个都没有则返回 null
```

- `ACCEPT = 16`,`GAME_BUDGET = 120`(强玩家对局数,按局计,不按时间计)。一个候选最多要 12 局(认证 3 + 三档需求各 3),所以在难的关上通常是预算先用完、攒不满 16 个——那时就在已收入的里面挑。简单的候选赢得早,只花一两局。
- **上限必须是计数不能是时间。**生成器有一条由测试钉住的约定:同一个 id 永远生成同一关(`the generator takes no input but its id`)。按秒截断会让输出依赖机器快慢。
- 种子从 `(id, 候选在排序里的序号, 车位数, 第几次尝试)` 派生。
- 机器人的 `judge` 不再参与第二遍:1.2 证明它的"死局"判定会扔掉大批可玩的窄配色,用它初筛会丢掉这个改动的主要收益。
- `mistakeCost` 不再参与排序(它是机器人的数,且此前已证明是噪声)。`gen-levels.ts` 的表格仍然打印它。
- `DEMAND_CURVE` 数值不变(第 1 关 1,其后 4),含义改为"强玩家车位需求的目标"。注释同步改写。

### 2.3 兜底

- 某个打包一个都认证不了 → `choosePainting` 返回 null,`generateLevel` 按现有逻辑换下一个打包;全部失败时走现有兜底路径。这种关卡未经认证,`npm run check` 会报错,不会悄悄发出去。
- 第 1 关(手写教学关)与颜色数 ≤ `UNLOCKED` 的关照旧不进入配色搜索。
- 隧道关无需特殊处理:强玩家直接在 `GameCore` 上打,隧道规则是 core 自带的。

### 2.4 慢检查 `npm run check`

新增 `tools/check-difficulty.ts`,编译方式与 `npm run gen` 相同(`tsconfig.gen.json` 加入该文件)。对第 2–10 关的**出货文件**:

- 跑 `certifyThreeStar`,再跑 `strongDemand`;
- 打印表格:关卡、三星认证、强玩家车位需求、width、机器人车位需求(对照用);
- 任何一个打包关认证不了三星就非零退出。

`level-gen.test.ts` 里这两条测试搬到这里:
- `three stars are reachable on the bay every level ships with`
- `every packed level asks for the whole bay`

它们断言的事情现在要由强玩家来回答,而强玩家跑九关远超单元测试能承受的时长。

## 3. 测试

### 3.1 `npm test`(快)

新增 `logic/tests/search-player.test.ts`:

1. **分叉精确**:一局打到中途分叉,两边用同一个确定性走法打到终局,状态签名(胜负、买的车位、剩余乘客、剩余车数)完全一致。
2. **分叉隔离**:在分叉那一边点一辆车,原局的车数不变。
3. **确定性**:同一关、同一种子打两遍,结果一样。
4. **强度**:一个机器人组在少车位时过不了、强玩家过得了的关卡。优先手工构造一个十来辆车的小关;凑不出来就用出货的第 4 关三车位(实测约 30 秒)。
5. **边界**:`play-sim.test.ts` 里现有的 `soloLevel` 能通过三星认证、`strongDemand` 为 1;`hopelessLevel` 认证失败。

`level-gen.test.ts`:删掉 2.4 列出的两条;`the generator takes no input but its id` 那条源码检查必须继续通过——新模块里不能出现 `Math.random`、`Date.now`。

### 3.2 验收顺序

1. 两道闸门:`npm test`、`npm run typecheck:view`。
2. 重生成第 2–10 关(预计每关 30–90 分钟,全量 6–10 小时,过夜跑)。
3. `npm run check` 全部通过。
4. 给出新旧对照表:每关强玩家车位需求与 width,新版对出货版。

## 4. 风险

- **收益可能不均匀。**1.3 的数据显示第 4 关能从 2 个车位涨到 3 个,第 10 关只能变窄、需求不变。很可能九关里只有少数几关的车位需求真正上涨,其余主要是变窄。对照表会如实给出。
- **需求是上界。**比强玩家更聪明的人可能少用一个车位。
- **强玩家自身的盲区。**它不穷举,某些真实存在的解它找不到;这会让一些实际可玩的配色被当作"认证不了"丢掉——方向是偏保守,不会把不可玩的关卡发出去。
- **生成时长。**九关全量重生成从半小时量级变成过夜。`npm run gen -- --only N` 仍然可用,单关不受其他关影响。

## 5. 不在本次范围

- 缩短预警时间(`lookahead` / planning window)。
- 开局少给车位(`UNLOCKED` 按关卡取值)。1.1 的数据显示强玩家在出货关卡上普遍只用 2–3 个车位,这个方向的依据比之前充分,但本次不做。
- 调色板扩充、第 11 关:已回退,代码留在 `stash@{0}`。
